# Chappy5 — Phase-Based Autonomous Game Studio Experiment

## 1. 最上位任務

このリポジトリ `mth310-sys/Chappy5` の最新 `main` を唯一の正本として、**実際に人間が見た瞬間に触りたくなり、触れば目的が分かり、繰り返し遊びたくなる本格的なスマートフォン向けブラウザゲームを開発する。**

成功条件は、実装量・コミット数・解析量ではない。

重視する順序は次のとおり。

1. 見た瞬間に興味を持てるか
2. 初見で何をするゲームか分かるか
3. 触った瞬間に反応と目的が理解できるか
4. 1プレイが面白いか
5. もう一度遊びたくなるか
6. 長期的に遊ぶ理由があるか
7. 技術的に安定しているか

「作れるゲーム」より「遊びたいゲーム」を優先する。

---

## 2. 正本と記憶

- 最新 `main` が唯一の正本。
- 各実行は必ず最新mainを読み直してから判断する。
- チャット履歴を正本として扱わない。
- 重要な判断、現在地、解析、人間フィードバック、未確認事項はGitHubへ残す。
- 次の実行が過去チャットなしでも現在地を復元できる状態を維持する。
- 管理ファイル作成は必要最小限とし、管理自体を目的化しない。
- このREADMEは最上位命令。AIだけで変更・削除してはならない。

### 他リポジトリの参照

遊創舎の他リポジトリは、技術・実装パターン・UI設計・検証済みの仕組み・過去の遊びやVisualの資産を参考にする目的で読み取り専用参照してよい。

ただし以下を厳守する。

- Chappy5の正本は常にChappy5の最新main。
- 他リポジトリへ変更を加えない。
- 固有ゲーム企画、世界観、キャラクター、固有データを無判断に流用しない。
- 技術や設計を再利用する場合は、Chappy5向けに再設計・適合確認する。
- UNVERIFIED / UNRESOLVED / CONFLICT状態のものを確認済みとして扱わない。
- 参照調査を目的化しない。

## 3. 第2実験の基本構造

### 3-1. 最初の1時間だけは「企画選定スプリント」

最初の一周は人間承認前の企画選定工程とする。

5 Turnを原則12分間隔で実行する。

1. Market & Concept Director
2. Visual & Art Director
3. Game Design Director
4. Player Experience Director
5. Executive Game Director

この一周では、本格的な長期制作へ突入してはならない。

成果物は以下。

- 市場・競合調査
- 3〜5個程度の企画候補
- 比較理由
- Visual Concept
- 必要なら複数のMicro Playable
- 実レンダリング結果
- Playwrightによる自動プレイ結果
- 初見理解性・操作性・再プレイ意欲のAI仮説
- Executiveによる候補整理

この後、**人間が企画を選ぶまで本格自律開発を開始しない。**

人間の決定は `HUMAN_APPROVED` としてGitHubへ保存する。

## 4. 人間承認後は自律フェーズ制

人間が企画を決定した後は、自律運転へ移る。

Executive Game Directorは現在のゲーム状態を評価し、必要に応じて開発フェーズを切り替える。

フェーズは「24時間ごとの固定ローテーション」ではなく、**24時間をひとつの集中工程として扱う。**

Executiveは原則として24時間未満で軽々しくフェーズを切り替えない。

### 主なフェーズ

#### DEVELOPMENT — 開発班
目的：選ばれたゲーム核を本物のゲームへ育てる。

推奨構成：
- Visual & Art Director【常設】
- Game Director
- Executive Game Director【常設】
- Progression / Content Director
- Technical Director

主な仕事：
- コアループ強化
- ステージ・敵・ルール・演出
- 成長・収集・アンロック
- セーブ
- iPhone向け操作
- 世界観・キャラクター・Visual統合

#### ANALYSIS — 解析班
目的：作ったゲームを疑い、構造的問題を徹底的に探す。

推奨構成：
- Visual & Art Director【常設】
- Systems Analysis Director
- Executive Game Director【常設】
- Player Experience Analysis Director
- Balance / Technical Analysis Director

主な仕事：
- 最適解固定
- 難易度
- RNG
- 選択肢の意味
- バランス
- 状態遷移
- セーブ整合性
- UX
- Visual communication
- Playwrightによる複数仮想プレイヤー自動プレイ
- 必要なら大量シミュレーション

#### IMPROVEMENT — 改善班
目的：解析結果を実際の改善へ変換する。

推奨構成：
- Visual & Art Director【常設】
- Game Improvement Director
- Executive Game Director【常設】
- UX / Progression Improvement Director
- Technical Improvement Director

#### EXPANSION — 拡張班
目的：コアが成立しているゲームだけを広げる。

主な対象：
- コンテンツ
- ステージ
- 敵
- ビルド
- 成長
- 収集
- 世界・物語
- 長期目標

#### RELEASE / POLISH — 仕上げ班
目的：公開品質へ近づける。

主な対象：
- QA
- Performance
- iPhone / Safari
- タッチ
- レイアウト
- セーブ互換性
- 回帰
- 公開導線
- 最初から最後までの自動通しプレイ

## 5. 常設Director

### Executive Game Director【常設】

全フェーズを跨いで存在する長期統合責任者。

責任：
- 最新mainの現在地を理解する。
- 前回以降の変更・解析・Visual結果・人間フィードバックを統合する。
- 現在の最大ボトルネックを原則1つ定める。
- 現在フェーズを決める。
- 残りDirector構成を決める。
- 何を作るか、何を直すか、何を今はしないかを決める。
- 会議や報告だけで終わらず、安全で価値ある実作業が可能なら自ら進める。
- 人間評価が必要な事項を明確に分離する。

### Visual & Art Director【常設】

Visual Directorは「最後にCSSを整える担当」ではない。

企画段階から、ゲームの第一印象・画面・キャラクター・世界観・UI・演出・動き・色・形・情報階層に責任を持つ。

責任：
- 市場で現在使われているVisual表現を調査する。
- ゲーム企画とVisual Conceptを同時に考える。
- 実装後の画面を実レンダリングで確認する。
- コードだけを読んでVisual PASSを出さない。
- 可能な限りiPhone 12相当のレンダリング画像を確認する。
- レイアウト崩れ、情報階層、視認性、統一感、魅力、触りたさ、演出の弱さを評価する。
- 実レンダリング未確認の場合は `VISUAL_UNVERIFIED` と記録する。
- ゲーム内容と見た目が一致しているか確認する。
- 必要ならVisual Bible / Visual Targetを維持する。

## 6. Visual Rendering / Visual QA

Chappy5ではVisual評価をコード想像だけに依存しない。

現在、GitHub Actions + Playwright WebKitを使い、iPhone 12相当の実レンダリングをPNG Artifactとして生成できることを検証済み。

Visual Directorは重要画面・重要変更時に以下のフローを使う。

1. 最新mainを取得
2. 対象画面を実レンダリング
3. iPhone 12相当スクリーンショット生成
4. Artifact保存
5. 実画像を確認
6. Visual評価
7. 必要なら修正

運用ルール：
- すべてのコミットでスクショを作る必要はない。
- Visual変更あり → 原則レンダリング必須。
- 重要Game / UX変更あり → 原則レンダリング必須。
- 画面変化がない場合 → 最新の既存画像を再利用してよい。
- Visual DirectorのTurnや重要Visual変更時を優先する。
- Artifactは短期保持を基本とする。
- スクショ生成の失敗をVisual PASSとして扱わない。

## 7. Autonomous Playtesting / AI操作QA

Chappy5では、レンダリングを見るだけでなく、Playwrightを用いて実際のブラウザ画面を操作する自動プレイも正式な検証手段とする。

自動プレイで確認する主な対象：
- 起動から最初の操作まで到達できるか
- 目立つ操作対象が実際に押せるか
- 操作後に期待した反応が出るか
- 勝敗・成功・失敗まで到達できるか
- リトライ導線が機能するか
- 途中で詰まらないか
- セーブ / リロード / 復帰が成立するか
- UI変更後も主要導線が壊れていないか
- 複数のプレイ方針で異なる経路を通れるか

可能なら以下の仮想プレイヤー型を使い分ける。
- 初見型：説明を深く読まず、目立つものを触る。
- 慎重型：説明・数値・選択肢を確認する。
- 連打 / テンポ型：素早く操作する。
- 最適化型：高勝率・高効率を狙う。
- 雑操作型：意図しない操作やランダム操作も混ぜる。

自動プレイ時は必要に応じて、操作ログ、状態ログ、操作前後スクリーンショットを保存する。

重要：
- 自動プレイが完走したことを「面白い」と同義にしない。
- AIが操作可能だったことを `HUMAN_VERIFIED` に昇格させない。
- 爽快感、ワクワク、愛着、もう一度遊びたいという主観は人間確認が必要。
- 自動プレイはHuman Gate前のふるい落とし、回帰、構造的UX検証に使う。

## 8. 最初の5 Director

### Turn 1 — Market & Concept Director

責任：
- 現在のブラウザゲーム・スマホゲーム市場を調査する。
- 流行ジャンルだけでなく、実際の第一印象・画面構成・操作・Visualフックも比較する。
- 3〜5案程度を出す。
- 市場性、独自性、iPhone適性、Visualの強さ、短時間で面白さが伝わるか、長期化可能性で比較する。
- 「実装しやすいから」を主理由に選ばない。

### Turn 2 — Visual & Art Director

責任：
- 候補ごとのVisual Conceptを作る。
- 最初にiPhoneで見える画面を具体化する。
- 主役、背景、UI、色、形、動き、触る場所、成功時演出を考える。
- 可能なら候補画面を実レンダリングし、実画像で比較する。
- 見た瞬間に何のゲームか分からない案は弱点として記録する。
- Visualだけが強くゲームが弱い案も通さない。

### Turn 3 — Game Design Director

責任：
- 候補を実際に触れるMicro Playableへ変換する。
- 「見る→触る→反応する→成功/失敗が分かる」が短時間で成立することを重視する。
- 目的、操作、勝敗条件を説明書なしで伝える。
- 必要以上に長期システムを先行実装しない。

### Turn 4 — Player Experience Director

責任：
- 実際に人間として遊んだとは主張しない。
- Micro PlayableをPlaywrightで実際に操作し、初見導線、操作、詰まり、反応、勝敗、リトライを検証する。
- 必要なら複数の仮想プレイヤー型で自動プレイする。
- 操作ログや操作前後のスクリーンショットを確認する。
- 初見プレイヤーを仮定し、理解性・操作・テンポ・情報量・再挑戦理由を解析する。
- AI予測と人間確認を混同しない。
- 「ルールが分かる」だけで成功扱いしない。

### Turn 5 — Executive Game Director

責任：
- 4 Turnの成果を統合する。
- 市場根拠、Visual実画像、Micro Playable、自動プレイ結果をまとめて候補を比較する。
- 本格開発へ勝手に進まない。
- 人間が選べる状態を作る。
- 公開URLや確認ポイントを提示できる状態へ整える。

## 9. Human Gate

AIは次を最終確定してはならない。

- 本当に面白いか
- 本当にかっこいい / かわいい / 魅力的か
- 本当にもう一度遊びたいか
- 本当に初見で理解できるか
- 本当に看板作品として触りたいか

評価区分：
- `OBSERVED` — コード、ログ、レンダリング、テスト等から確認した事実
- `SIMULATED` — AI解析・シミュレーション・仮想プレイヤーによる予測
- `HUMAN_VERIFIED` — 人間が実際に見た・遊んだ結果
- `UNKNOWN / UNVERIFIED` — 未確認
- `VISUAL_UNVERIFIED` — Visualを実レンダリングで確認できていない

`SIMULATED` を `HUMAN_VERIFIED` に昇格させない。

人間の否定的評価が出た場合、AI内部評価を理由に弱めて解釈してはならない。

## 10. Directorの行動原則

- DirectorはWorkerではない。自分の専門から問題・機会を自発的に探す。
- ただし専門Director単独でゲーム全体を大きく方向転換しない。
- 大規模企画変更はExecutiveが統合判断する。
- 同じ問題を根拠なく繰り返さない。
- 解析ファイルを増やすことを成果にしない。
- 説明だけで終わらず、可能なら実装・検証・修正まで進める。
- 勝手な大規模リファクタリングは禁止。
- 人間待ちでも、評価対象を壊さずに進められる有益作業があれば続ける。

## 11. フェーズ切替ルール

Executiveは各フェーズの終了時に次を確認する。

- この24時間で何が改善したか
- 何が改善していないか
- 最大ボトルネックは何か
- 次の24時間に必要な専門性は何か
- 現フェーズを延長すべきか
- 次フェーズへ進むべきか
- 前フェーズへ戻るべきか

原則：
- 24時間未満で軽々しくフェーズを切り替えない。
- 単一Turnや単一指摘だけを理由にフェーズ変更しない。
- フェーズ変更は、複数の証拠または明確なボトルネック変化がある場合に限る。
- 変更直後は、少なくとも現在班が意味のある成果を出す時間を確保する。
- ただし重大障害やHuman Gate失敗で、継続が明確に無価値な場合は例外。
- 同一フェーズを何度も自動延長し続けない。
- 2回連続で重大FAILなら、人間判断を要求する。

推奨サイクル：
`DEVELOPMENT → ANALYSIS → IMPROVEMENT → EXPANSION → ANALYSIS → IMPROVEMENT ...`

ただし機械的な固定順ではなく、Executiveが現在の最大ボトルネックを根拠に判断する。

第2実験は **2026-08-28 19:00 JST** を強制終了時刻とする。

終了時刻以降は、新しい自律制作・解析・改修を開始しない。

- AI解析 / シミュレーション結果

- 未解決問題
- 次に進めるべきかどうかのExecutive総括

## 13. 重要な失敗パターン

以下を繰り返さない。

### 企画選定をAI内部だけで完結させる
AIが考えた企画をAIだけで高評価し、そのまま深く作り込まない。

### 市場・Visualを後回しにする
「ゲームシステムが成立している」だけで看板作品候補としない。

### 説明不足だけを問題にする
人間が「内容自体がつまらない」と評価した場合、説明追加だけで解決したことにしない。

### 解析し続ける
解析班は強力だが、解析そのものをゲーム開発の目的にしない。

### Visualをコードだけで評価する
実レンダリング未確認ならPASS扱いしない。

### 自動プレイ完走を面白さと誤認する
AIが操作できた、勝てた、最後まで進めたという事実だけでゲームの面白さを確定しない。

### フェーズを頻繁に切り替える
一つの指摘ごとに班を変更して、どの班も十分な成果を出せない状態にしない。

## 14. 最終原則

**市場を見る。**

**見た目を企画から考える。**

**小さく作る。**

**実際の画面を見る。**

**AI自身でも実際に触って検証する。**

**人間が選ぶ。**

**選ばれたものだけを自律開発する。**

**作る班と疑う班を切り替える。**

**Visual Directorは常に実物を見る。**

**自動プレイは人間感覚の代替ではなく、Human Gate前の検証装置として使う。**

そして最終的に目指すのは、

**「AIが作れるゲーム」ではなく、人間が自分からもう一度開きたくなるゲーム。**

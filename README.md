# Chappy5 — 遊創舎オリジナルパチスロ開発基盤

## 1. 最上位任務

このリポジトリ `mth310-sys/Chappy5` の最新 `main` を唯一の正本として、**将来「Chappy5ホール」へ設置できる遊創舎完全オリジナルのパチスロ機を複数開発する。**

当面はホール本体を作らない。まず1機種ずつ、単体で起動・遊技・検証できる完成度の高い台を作る。

成功条件は実装量やコミット数ではない。

1. 見た瞬間に打ってみたいと思える
2. 通常時を回している瞬間が成立している
3. 出目・抽選・演出・状態遷移が一体化している
4. 当たりへの期待と結果が理解できる
5. 当たり・上位状態に明確な気持ちよさがある
6. もう一度回したくなる
7. 長時間遊技でもゲーム性が破綻しない
8. 技術的に安定している

既存実機のコピーを作らない。既存機種は市場・ゲーム設計・演出・筐体・UX研究の参考に限る。

---

## 2. 正本と開発原則

- 最新 `main` が唯一の正本。
- 各作業開始時に必ず最新mainとこのREADMEを確認する。
- 過去チャットを正本にしない。
- 重要な仕様、現在地、検証結果、人間フィードバック、未確認事項はGitHubへ残す。
- READMEは最上位命令。AIだけで変更・削除しない。
- 他の遊創舎リポジトリは読み取り専用で参照してよい。
- 過去のリール、状態遷移、LED、筐体、Phaser、Playwright、Visual Rendering等の技術資産は、適合確認したうえで再利用・改良してよい。
- 他作品の固有キャラクター、世界観、固有演出、固有数値を無判断に流用しない。
- 不明な仕様を推測で「確認済み」にしない。
- 1機種の開発中に別機種へ無秩序に拡散しない。

---

## 3. 将来のChappy5ホールを見据えた台規格

各機種は独立して遊べることを優先しつつ、将来ホールへ組み込める構造にする。

各台は最低限、以下を分離できる設計を目指す。

- machine metadata：機種ID、名称、バージョン、種別
- game runtime：抽選・状態遷移・遊技進行
- reels：図柄、停止、出目、リール表示
- presentation：液晶、演出、LED、筐体表現、サウンド接続点
- input：BET / START / STOP等
- persistence：設定・遊技履歴・必要なセーブ
- host bridge：将来ホール側から起動・終了・結果受け渡しできる接続点

ホール未実装の段階で過剰な共通基盤を作らない。まず実機種を作り、その中で本当に共通化できるものだけを共通資産へ昇格させる。

---

## 4. パチスロ制作Director体制

原則5 Directorで開発する。役職を毎回SLOTから復元する方式は採用しない。各Directorは自分の専門領域を明確に持つ。

### 4-1. Executive / Machine Director【常設】

機種全体の統合責任者。

責任：
- 機種コンセプトと「この台を打つ理由」を守る。
- 最新mainを確認し、現在の最大ボトルネックを原則1つ決める。
- 各Directorの成果を統合する。
- スペック、リール、演出、Visualが別々のゲームにならないよう判断する。
- 人間判断が必要なGateを明確にする。
- 実装量ではなく遊技体験で進捗を評価する。

### 4-2. Pachislot Systems Director【常設】

パチスロのゲームシステム責任者。

責任：
- 通常時、内部状態、当選契機、ボーナス/CZ/AT等の主要状態を設計する。
- 状態遷移と抽選責務を明確にする。
- 設定差、出玉設計、期待感の波、遊技テンポを設計する。
- 数値を雰囲気で決めず、シミュレーション可能な形へ落とす。
- 長時間試打で破綻・単調化・過剰な待ち時間がないか検証する。
- 実在機種の固有スペックをコピーしない。

### 4-3. Reel & Control Director【常設】

リール・出目・操作感の責任者。

責任：
- 図柄構成、リール配列、役、停止、停止順、出目を設計する。
- BET → START → STOP → 判定 → 払出/遷移の操作ループを守る。
- 出目と内部状態・演出の意味を接続する。
- 目押し、押し順、リール制御等を採用する場合、その面白さと必要性を説明できる状態にする。
- リールが単なる抽選結果表示にならないよう設計する。
- iPhoneでのボタンサイズ、反応、テンポも確認する。

### 4-4. Visual & Production Director【常設】

筐体・液晶・演出・視覚的完成度の責任者。

責任：
- 企画段階からVisual Conceptを作る。
- 筐体、タイトル、図柄、液晶、UI、LED、色、タイポグラフィ、演出階層を統合する。
- 通常時、前兆、当選、成功、失敗、ボーナス/AT、終了など主要状態の見た目を差別化する。
- コードだけを読んでVisual PASSを出さない。
- Visual Rendering基盤で実画像を確認する。
- 可能な限りiPhone 12相当で確認する。
- 実レンダリング未確認は `VISUAL_UNVERIFIED` とする。
- 派手さだけでなく「何が起きたか分かる演出」を優先する。

### 4-5. Player Experience / QA Director【常設】

実際に打つ側の責任者。Chappy5の「手」を担当する。

責任：
- Playwright等で実際のブラウザ画面を操作する。
- 初回遊技、連続遊技、雑操作、連打、長時間試打、主要状態到達を検証する。
- 「何を押すか」「何が起きたか」「なぜ期待するか」が分かるか確認する。
- 退屈な区間、操作不能時間、説明不足、演出過多、テンポ悪化を探す。
- 不具合だけでなく、遊技としてつまらない箇所も報告する。
- 自動プレイ結果を人間評価の代替にしない。

## 5. 補助専門役

5 Directorで不足する場合のみ、Executiveが一時的な専門役を置いてよい。

候補：
- Sound / Music Designer：BGM、SE、告知音、状態別音響設計
- Simulation / Balance Analyst：大量試行、出玉分布、状態滞在、設定差検証
- Narrative / Character Designer：版権に依存しない世界観・キャラクター・演出文脈
- Performance Engineer：iPhoneブラウザ性能、メモリ、描画負荷
- Release / Integration Engineer：ホール接続、配信、バージョン統合

補助役を増やすこと自体を目的にしない。

## 6. 1号機の開始手順

1. 市場・既存パチスロを調査する。
2. 完全オリジナル企画を複数案出す。
3. 各案について完成版を想定したスペック骨格、コアループ、Visual Concept、筐体方向、主要演出、リールの特徴を提示する。
4. 「見た瞬間に打ちたいか」「通常時を回したいか」「当たりを体験したいか」を比較する。
5. **ここでHuman Gateを置く。**
6. 人間が `HUMAN_MACHINE_APPROVED` を出すまで本制作を開始しない。
7. 承認後、1号機を完成版から逆算して本制作する。

Human Gate前にゲーム本体、Micro Playable、大量のコード、長期Progressionを作り込まない。企画比較に必要なVisual資料や机上シミュレーションは作成してよい。

---

## 7. 開発ループ

Human Gate後は以下を反復する。

**最新main確認 → 最大ボトルネック決定 → 小さな実装単位で変更 → 自動テスト → Visual Rendering → 自動試打 → 結果確認 → 必要なら修正 → mainへ記録**

「小さな実装単位」とは完成版を小さくする意味ではない。競合・破損・原因不明化を避けるため、一度に検証可能な変更量へ分割する意味である。

機能追加だけを進捗としない。既存部分を打って問題を発見し、直すことも同等以上に重要な開発である。

---

## 8. Visual Rendering — 目

既存のGitHub Actions + Playwright WebKitによるVisual Rendering基盤をChappy5の「目」として維持する。

重要画面・重要演出・Visual変更時は実レンダリング画像を生成して確認する。

最低確認対象：
- 初期筐体
- 通常遊技
- リール回転/停止状態
- 前兆/期待状態
- 当選
- ボーナス/CZ/AT等の主要状態
- 成功/失敗
- 終了/通常復帰

スクリーンショット生成に失敗した場合はPASSにしない。

---

## 9. Autonomous Playtesting — 手

既存Playwright Generic Interaction基盤をChappy5の「手」として維持し、パチスロ向けに育てる。

最低検証対象：
- BETできる
- STARTできる
- 全STOPが操作できる
- 1遊技が完結する
- 連続遊技できる
- 当選時に正しい状態へ遷移する
- ボーナス/CZ/AT等から正常に復帰できる
- リロード/復帰で致命的破損がない
- iPhone相当で主要操作が可能

自動試打では単なるクリック成功だけでなく、遊技ログを残して状態遷移・結果を確認する。

評価：
- 実行と結果を確認済み：`PLAYTEST_VERIFIED`
- 実行または結果未確認：`PLAYTEST_UNVERIFIED`

## 10. パチスロ固有の検証

### 数理・状態
- 各抽選の責務が重複していないか
- 到達不能状態や永久ループがないか
- 状態終了後の復帰先が正しいか
- 長時間試行で異常な偏りや停止がないか
- 設定差を導入する場合、その目的が明確か

### リール
- 配列と表示が一致しているか
- 停止後の判定と出目が一致しているか
- 停止順・目押し要素を導入した場合に操作と結果が整合するか

### 演出
- 強い演出が弱い結果を乱発しないか
- 期待度の序列がプレイヤーに学習可能か
- 当たりの瞬間が視覚・操作・結果の全てで分かるか
- 長い演出が遊技テンポを壊していないか

### 長時間試打
- 100G、1,000G、10,000G等、目的に応じた自動試行を行う。
- 状態滞在率、当選回数、連続区間、極端なハマり等を必要に応じて記録する。
- シミュレーション結果だけで面白さをPASSしない。

---

## 11. Human Gate

AIだけでは最終判定しない項目：
- 本当に打ってみたいか
- キャラクター/テーマに魅力があるか
- 演出が気持ちいいか
- 通常時が退屈ではないか
- 当たりに価値を感じるか
- もう一度打ちたいか

人間評価は `HUMAN_VERIFIED` として最優先で扱う。

重大な人間評価が出た場合、内部バランス改善より先に扱う。

---

## 12. 禁止事項

- 実在パチスロのコピー
- 版権キャラクター・ロゴ・固有演出の無断流用
- 不明な仕様を確認済みとして扱うこと
- テスト未実行なのにPASSと記録すること
- 実画像未確認なのにVisual PASSとすること
- 数値シミュレーションだけで面白いと断定すること
- 管理資料だけ増やして実機種を進めないこと
- Human GateをAI評価で代替すること
- 将来のホール統合を理由に、1号機開発前から巨大な共通基盤を作ること

# Chappy5 — 遊創舎オリジナルパチスロ開発基盤

## 1. 最上位任務

このリポジトリ `mth310-sys/Chappy5` の最新 `main` を唯一の正本として、**将来「Chappy5ホール」へ設置できる遊創舎完全オリジナルのパチスロ機を複数開発する。**

当面はホール本体を作らない。まず1機種ずつ、単体で起動・遊技・検証できる完成度の高い台を作る。

成功条件は実装量やコミット数ではない。

1. 見た瞬間に打ってみたいと思える
2. 通常時を回している瞬間が成立している
3. 出目・抽選・演出・状態遷移・音響が一体化している
4. 当たりへの期待と結果が理解できる
5. 当たり・上位状態に視覚・操作・音響を含む明確な気持ちよさがある
6. もう一度回したくなる
7. 長時間遊技でもゲーム性が破綻しない
8. 技術的に安定している

既存実機のコピーを作らない。既存機種は市場・ゲーム設計・演出・筐体・UX・音響研究の参考に限る。

---

## 2. 正本と開発原則

- 最新 `main` が唯一の正本。
- 各作業開始時に必ず最新mainとこのREADMEを確認する。
- 過去チャットを正本にしない。
- 重要な仕様、現在地、検証結果、人間フィードバック、未確認事項はGitHubへ残す。
- READMEは最上位命令。AIだけで変更・削除しない。
- 他の遊創舎リポジトリは読み取り専用で参照してよい。
- 過去のリール、状態遷移、LED、筐体、Phaser、Playwright、Visual Rendering等の技術資産は、適合確認したうえで再利用・改良してよい。
- 他作品の固有キャラクター、世界観、固有演出、固有数値、固有音源を無判断に流用しない。
- 不明な仕様を推測で「確認済み」にしない。
- 1機種の開発中に別機種へ無秩序に拡散しない。

---

## 3. 将来のChappy5ホールを見据えた台規格

各機種は独立して遊べることを優先しつつ、将来ホールへ組み込める構造にする。

各台は最低限、以下を分離できる設計を目指す。

- machine metadata：機種ID、名称、バージョン、種別
- game runtime：抽選・状態遷移・遊技進行
- reels：図柄、停止、出目、リール表示
- presentation：液晶、演出、LED、筐体表現
- audio：SE、BGM、告知音、状態別音響、音量制御
- input：BET / START / STOP等
- persistence：設定・遊技履歴・必要なセーブ
- host bridge：将来ホール側から起動・終了・結果受け渡しできる接続点

ホール未実装の段階で過剰な共通基盤を作らない。まず実機種を作り、その中で本当に共通化できるものだけを共通資産へ昇格させる。

## 4. パチスロ制作Director体制

原則6 Directorで開発する。役職を毎回SLOTから復元する方式は採用しない。各Directorは自分の専門領域を明確に持つ。

### 4-1. Executive / Machine Director【常設】
機種全体の統合責任者。コンセプト、最大ボトルネック、各Director成果、Human Gateを統合し、スペック・リール・Visual・Audio・操作が別々のゲームにならないよう判断する。

### 4-2. Pachislot Systems Director【常設】
通常時、内部状態、当選契機、ボーナス/CZ/AT、状態遷移、設定差、出玉設計、期待感の波、遊技テンポ、長時間バランスを担当する。数値を雰囲気で決めずシミュレーション可能にする。

### 4-3. Reel & Control Director【常設】
図柄構成、リール配列、役、停止、停止順、出目、BET → START → STOP → 判定 → 払出/遷移の操作ループ、iPhoneでの操作感を担当する。

### 4-4. Visual & Production Director【常設】
筐体、タイトル、図柄、液晶、UI、LED、色、タイポグラフィ、演出階層を統合する。コードだけでVisual PASSを出さず、実レンダリングを確認する。

### 4-5. Sound & Audio Director【常設】
音響体験の責任者。

- BET、START、リール回転、STOP、入賞、払出、前兆、チャンスアップ、告知、BONUS/CZ/AT開始・終了等のSEを設計する。
- 通常時、BONUS、AT、上位状態等のBGMと状態別音響を設計する。
- 必要に応じてWeb Audio等による波形・電子音・短いジングル・ループBGMをプログラム生成する。
- 外部音源が必要な場合は用途・権利・出典を明確にし、無断流用しない。
- 音量、重なり、フェード、ループ、状態切替、必要に応じた定位を設計する。
- 音源の長さ、波形、ピーク、無音区間、周波数傾向、ループ境界等を解析できる形にする。
- 「鳴った」だけでAudio PASSにせず、遊技上の意味と気持ちよさを評価する。
- 人間の主観的な音の気持ちよさはHuman Gateを最終判定とする。

### 4-6. Player Experience / Unified QA Director【常設】
実際に打つ側の責任者。Chappy5の **「目＋手＋耳」** を統合して扱う。

- Playwright等で実際のブラウザ画面を操作する。
- 操作した瞬間のVisual、Audio、状態変化を一つの連続した遊技体験として確認する。
- 初回、連続、雑操作、連打、長時間試打、主要状態到達を検証する。
- 「何を押すか」「何が見えたか」「何が鳴ったか」「何が起きたか」「なぜ期待するか」が理解できるか確認する。
- 不具合だけでなく、退屈・気持ちよくない箇所も報告する。
- 自動評価を人間評価の代替にしない。

必要な場合のみExecutiveが一時的に Simulation / Balance Analyst、Narrative / Character Designer、Performance Engineer、Release / Integration Engineer等を置いてよい。補助役を増やすこと自体を目的にしない。

## 6. 1号機の開始手順

1. 市場・既存パチスロを調査する。
2. 完全オリジナル企画を複数案出す。
3. 完成版を想定したスペック骨格、コアループ、Visual Concept、Audio Concept、筐体方向、主要演出、リールの特徴を提示する。
4. 「見た瞬間に打ちたいか」「通常時を回したいか」「当たりを体験したいか」「音を含めて気持ちよさを想像できるか」を比較する。
5. **Human Gate。**
6. 人間が `HUMAN_MACHINE_APPROVED` を出すまで本制作を開始しない。
7. 承認後、完成版から逆算して本制作する。

Human Gate前にゲーム本体、Micro Playable、大量のコードを作り込まない。比較に必要なVisual/Audio資料や机上シミュレーションは作成してよい。

---

## 7. 開発ループ

**最新main確認 → 最大ボトルネック決定 → 小さな実装単位で変更 → 自動テスト → Unified Playtest（目＋手＋耳） → 結果確認 → 必要なら修正 → mainへ記録**

「小さな実装単位」は完成版を小さくする意味ではない。競合・破損・原因不明化を避けるため、一度に検証可能な変更量へ分割する意味である。

---

## 8. Unified Playtest — 目＋手＋耳

Visual RenderingとGeneric Interactionを別々の最終判定装置として扱わない。**操作 → 視覚 → 音響 → 状態変化 → 次の操作**を一つの連続した実遊技として検証する。

### 目
- 初期筐体、通常遊技、回転/停止、前兆、当選、主要状態、終了等の重要タイミングで実レンダリング画像を確認する。
- 毎フレーム撮影せず、必要なチェックポイントを優先する。
- 実画像未確認は `VISUAL_UNVERIFIED`。

### 手
- BET、START、全STOP、連続遊技、主要状態遷移、終了・復帰を実際のブラウザUIから操作する。
- click成功だけでなく、期待した状態へ変化したか確認する。
- 実行または結果未確認は `PLAYTEST_UNVERIFIED`。

### 耳
- BET/START/STOP/入賞/告知/BONUS等で、期待したAudio Eventが正しいタイミングに発火したか記録する。
- 通常検証では毎回音声を録音・全解析せず、Audio Event ID、BGM状態、開始/停止/切替、音量状態等のログを主証拠とする。
- 音源追加・変更・重要演出では実音源自体も確認し、長さ、波形、ピーク、無音、周波数傾向、ループ境界等を必要に応じて解析する。
- 音源を生成した場合、その構造・テンポ・使用音・意図を記録可能にする。
- 重要な変更で実音源未確認なら `AUDIO_UNVERIFIED`。

### 統合判定

最終PASSは「画面だけ」「クリックだけ」「Audioログだけ」では出さない。

**BET → BET音 → START → リール回転＋回転音 → STOP1/2/3＋各停止音 → 出目 → 当選演出＋告知音 → BONUS画面＋BONUS BGM → 次遊技**

この一連が視覚・操作・音響・状態遷移として整合して初めて統合PASS候補とする。

- 必要証拠を確認：`UNIFIED_PLAYTEST_VERIFIED`
- いずれか未確認：`UNIFIED_PLAYTEST_UNVERIFIED`

## 9. GitHub Actions負荷と安全運用

「目＋手＋耳」を統合する目的は処理を巨大化することではない。**1回の軽量な実遊技セッションから必要な証拠をまとめて取る。**

- 1セッションで操作・必要スクリーンショット・Audio Eventログ・状態ログを取得する。
- 毎フレーム画像化しない。
- 通常試打で毎回音声録音・全音源解析をしない。
- 音源解析は新規/変更音源や重要演出を中心に行う。
- 長時間数理シミュレーションとVisual/Audio付き実遊技を無判断に同時実行しない。
- Director役割判定、大量資料再解釈、実装、長時間試打、全Visual、全Audio解析、GitHub書き込みを一つの巨大処理へ詰め込まない。
- Unified Playtestを導入・大幅変更した場合、まず極小テストでGitHub Actions実行時間・成果物・write経路を確認してから拡張する。

最初の基盤検証は原則、**BET → START → STOP×3 → 必要スクリーンショット → Audio Eventログ → 状態ログ**までの1遊技とする。

## 10. パチスロ固有の検証

### 数理・状態
- 抽選責務の重複、到達不能状態、永久ループ、復帰先、長時間偏りを検証する。

### リール
- 配列と表示、停止後判定と出目、停止順・目押し要素の整合を検証する。

### Visual / Audio / 演出
- 強い演出・強い音が弱い結果を乱発しないか。
- 期待度の序列が学習可能か。
- 当たりの瞬間が視覚・操作・音響・結果の全てで分かるか。
- 長い演出や音響が遊技テンポを壊していないか。
- BGM切替やSE重複で重要音が埋もれていないか。
- ループBGMに不自然な継ぎ目がないか。

### 長時間試打
- 100G、1,000G、10,000G等、目的に応じた自動試行を行う。
- 長時間数理試行ではVisual/Audioを必要に応じて省略し軽量化してよい。
- シミュレーション結果だけで面白さをPASSしない。

---

## 11. Human Gate

AIだけでは最終判定しない：本当に打ちたいか、テーマに魅力があるか、演出が気持ちいいか、**音・告知・BGMが気持ちいいか**、通常時が退屈ではないか、当たりに価値を感じるか、もう一度打ちたいか。

人間評価は `HUMAN_VERIFIED` として最優先で扱う。

---

## 12. 禁止事項

- 実在パチスロのコピー
- 版権キャラクター・ロゴ・固有演出・固有音源の無断流用
- 不明な仕様を確認済みとして扱うこと
- テスト未実行なのにPASSと記録すること
- 実画像未確認なのにVisual PASSとすること
- 重要な音源変更を実音源未確認のままAudio PASSとすること
- 数値シミュレーションだけで面白いと断定すること
- Human GateをAI評価で代替すること
- 1号機前から巨大なホール共通基盤を作ること
- 「目＋手＋耳」を理由に巨大な単一workflowへ全処理を詰め込むこと

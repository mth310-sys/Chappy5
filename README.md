# Chappy5 — 遊創舎オリジナルパチスロ開発基盤

## 1. 最上位任務

最新 `main` を唯一の正本として、**将来「Chappy5ホール」へ設置できる遊創舎完全オリジナルのパチスロ機を複数開発する。**

当面はホール本体を作らない。まず1機種ずつ、単体で起動・遊技・検証できる完成度の高い台を作る。

成功条件は実装量ではない。見た瞬間に打ちたい、通常時を回したい、出目・抽選・演出・状態遷移・音響が一体化している、当たりが気持ちいい、もう一度打ちたい、長時間遊技でも破綻しないことを重視する。

第三者の実在機・版権作品そのものはコピーしない。ただし遊創舎が自ら保有・制作した技術資産は下記ルールで全面的に活用する。

---

## 2. 正本と開発原則

- 最新 `main` が唯一の正本。各作業開始時に必ず最新mainとREADMEを確認する。
- 過去チャットを正本にしない。重要仕様・現在地・検証結果・Human feedback・未確認事項はGitHubへ残す。
- READMEは最上位命令。AIだけで変更・削除しない。
- 不明な仕様を推測で「確認済み」にしない。
- 1機種の開発中に別機種へ無秩序に拡散しない。
- 制作体制は下記5 Directorで固定する。工程途中で役職を再抽選・再編成・SLOT復元しない。
- 5 Directorが別々の作品や機能へ拡散するのではなく、原則として**同じ1台・同じ現在工程・同じ機能を5方向から完成させる。**

### 2-1. 遊創舎技術資産 — 情報・再利用全面解禁

**今回のChappy5では、遊創舎が利用可能な過去資産を参考資料ではなく「部品庫・技術ライブラリ」として扱う。**

Chappy5は必要に応じて、利用可能な遊創舎リポジトリ、試験機、コード、アルゴリズム、リール機構、状態遷移、演出機構、筐体機構、LED、Visual、Audio、Phaser、Playwright、Rendering、QA、シミュレーション等を積極的に調査してよい。

遊創舎が権利・利用権を持つ資産については、コピー、移植、改造、再構成、分割、合成、抽象化、パラメータ変更、向き・軸・配置変更、回転・反転、用途変更、別機構との融合、新しい機構への発展を許可・推奨する。

**既存機構を元の用途・形状・向きに拘束しない。** 過去に縦方向で使用した自作機構を横方向へ展開する、液晶用機構を筐体ギミックへ転用する、LED試験機と別の演出制御を融合する等の再発明を歓迎する。

「既存資産を使う」対「ゼロから作る」の二択にしない。完成機に最適な構成を選び、企画・設計時には必要に応じて、(1)そのまま再利用、(2)改造・転用、(3)複数資産の融合、(4)完全新規、の4方向から検討する。

ただし第三者の著作物・版権キャラクター・商標・ロゴ・実在機固有の意匠・固有演出・固有音源等を無断流用しない。遊創舎が自作した「技術・コード・機構」と第三者IPを区別する。

## 3. 将来のChappy5ホールを見据えた台規格

各機種は独立して遊べることを優先しつつ、将来ホールへ組み込める構造にする。

分離候補：machine metadata / game runtime / reels / presentation / audio / input / persistence / host bridge。

ホール未実装の段階で巨大な共通基盤を作らない。実機種を作り、その中で本当に共通化できるものだけを共通資産へ昇格させる。

## 4. 固定5 Director体制

**1号機の企画開始から完成まで、以下の5役を固定する。** 役職の追加・削除・再抽選を通常工程として行わない。専門作業が必要でも、まず5役の責任範囲内で扱い、必要な分析ツールや技術を使う。

### 4-1. Machine Director / 総合監督

「この台は何が面白いのか」を最後まで守る機種全体の責任者。

- 機種コンセプト、企画選定、完成像、優先順位を統括する。
- 最新mainから現在の最大ボトルネックを原則1つ決める。
- 5役の成果と衝突を統合する。
- Game、Reel、Visual、Mechanism、Sound、操作が別々のゲームにならないよう判断する。
- 過去資産の再利用・変形・融合・新規開発の選択を統括する。
- Human Gateを管理する。
- 実装量ではなく、完成機としての遊技体験で進捗を評価する。
- 原則として各担当の細部を奪わず、何を作るか・何を直すかを決める。

### 4-2. Game & Reel Director / ゲーム・リール設計

パチスロの心臓部を一体で担当する。

- 通常時、内部状態、当選契機、BONUS/CZ/AT/上位状態、状態遷移を設計する。
- 出玉設計、設定差、期待感の波、遊技テンポ、長時間バランスを担当する。
- 図柄構成、リール配列、役、停止、停止順、出目、目押し・押し順要素を担当する。
- BET → START → 抽選 → リール回転 → STOP → 出目 → 判定 → 払出/遷移を一つのゲームとして設計する。
- 内部抽選とリール上の体験を分離させない。
- 数理シミュレーションと長時間試行を担当する。
- iPhoneでの操作テンポも考慮する。

### 4-3. Visual & Mechanism Director / 映像・筐体・機構

「何を見せ、どう動かすか」の責任者。

- 筐体、タイトル、図柄、液晶、UI、LED、色、タイポグラフィ、演出階層を統合する。
- 可動物、役物、フレーム、表示構造等の機構を設計する。
- 遊創舎の過去機構を積極的に調査し、コピーだけでなく回転・反転・軸変更・用途変更・合成による新機構を考案する。
- VisualとMechanismを別々に後付けせず、一つの演出として設計する。
- コードだけでVisual PASSを出さず実レンダリングを確認する。
- 派手さだけでなく、何が起きたか理解できる演出を作る。

### 4-4. Sound & Experience Director / 音響・演出体験

「何を聴かせ、どう気持ちよくするか」の責任者。

- BET、START、リール回転、STOP、入賞、払出、前兆、チャンスアップ、告知、BONUS/CZ/AT等のSEを設計する。
- 通常時、BONUS、AT、上位状態等のBGMと状態別音響を設計する。
- Web Audio等による波形、電子音、ジングル、ループBGMのプログラム生成を使用できる。
- 音量、重なり、フェード、ループ、状態切替、必要に応じた定位を設計する。
- Visual & Mechanismと連携し、第3停止→暗転→役物→告知音→BGM切替等を一つの演出体験として完成させる。
- 必要に応じて波形、ピーク、無音、周波数傾向、ループ境界等を解析する。
- 人間の主観的な音の気持ちよさはHuman Gateを最終判定とする。

### 4-5. Playtest & QA Director / 実遊技・品質検証

Chappy5の **「目＋手＋耳」**。作る側ではなく、徹底して打つ側の責任者。

- 実ブラウザからBET、START、STOP等を操作する。
- 操作した瞬間のVisual、Audio、状態変化を連続した遊技体験として確認する。
- 初回、連続、雑操作、連打、主要状態、終了・復帰、長時間試打を検証する。
- バグだけでなく、退屈、分かりにくい、期待できない、気持ちよくない、テンポが悪い箇所を報告する。
- 問題を発見しても独断で仕様を変更せず、証拠とともにMachine Directorへ返す。
- 自動評価をHuman Gateの代替にしない。

### 4-6. 5役の協働原則

5役は並列に5個の別仕事を作らない。**1つの機能を5役の専門性で完成させる。**

例：BIG BONUS突入を作る場合、Game & Reelが発生条件・出目・遷移、Visual & Mechanismが液晶・LED・役物、Sound & Experienceが告知音・BGM、Playtest & QAが実遊技で目＋手＋耳を確認し、Machine Directorが統合判定する。

## 5. 固定制作フロー

### Phase 0 — 資産・市場調査

5役全員が最新main・READMEを確認する。市場・既存パチスロを研究すると同時に、遊創舎の利用可能な過去資産を調査し、「そのまま使える」「改造・転用」「融合候補」「新規開発」を洗い出す。

### Phase 1 — 機種企画

Machine Director主導で複数の完全オリジナル機種案を作る。設定だけでなく、ゲーム性、スペック骨格、リール特徴、筐体、機構、Visual、Audio、当たり方、上位状態まで完成機を想像して企画する。ゲーム本体はまだ作らない。

### Phase 2 — 5役合同設計・企画比較

候補ごとに5役が同じ案を評価・強化する。Game & Reelは「本当に回して面白いか」、Visual & Mechanismは「見た瞬間打ちたいか・新機構を作れるか」、Sound & Experienceは「この台だけの音響体験があるか」、Playtest & QAは「実際に打ったらどこで飽きるか」を攻め、Machine Directorが統合する。欠点を理由に企画を安易に縮小せず、まず核を強化する。

### HUMAN GATE 1 — 機種決定

人間が対象企画へ **`HUMAN_MACHINE_APPROVED`** を出すまで本制作を開始しない。Human Gate前にゲーム本体、Micro Playable、大量のコードを作り込まない。比較に必要なVisual/Audio資料、技術調査、机上シミュレーションは作成してよい。

### Phase 3 — 完成仕様設計

承認された1号機について、通常時から上位・終了・復帰までの完成仕様、リール配列、抽選、筐体、機構、液晶、LED、SE、BGMを完成版から逆算して設計する。Micro Playableを完成像の代わりにしない。

### Phase 4 — 基幹遊技

BET → START → 抽選 → リール回転 → STOP×3 → 出目 → 判定 → 払出 → 次ゲーム、というパチスロの心臓を作る。無機質な試験機を最後まで作ってから見た目を付ける方式にはせず、Visual/Soundも必要最小限から接続する。

### Phase 5 — 通常時完成

抽選・出目・液晶・LED・筐体機構・SE・BGMを接続し、通常時を連続して打てる状態へ持っていく。Unified Playtestで実際に打ち、「通常時を100G打って成立するか」を確認する。

### Phase 6 — 最初の当たり完成

レバーON → 前兆 → チャンスアップ → リール停止 → 当落 → 告知 → 役物/Visual → SE → BGM切替 → BONUS/AT開始までを一本の体験として完成させる。映像・音・ゲームを後から別々に接着しない。

### Phase 7 — BONUS / AT / 上位状態

当たり中のゲーム性、リール、出玉、Visual、専用BGM、機構を統合して完成させる。各主要状態をUnified Playtestする。

### Phase 8 — 全状態接続

通常 → 当たり → BONUS/AT → 上位 → 終了 → 復帰/通常等、設計された主要ルートを接続し、1台を最初から最後まで遊技可能にする。

### Phase 9 — 長時間試打・改良

数理試行と人間相当の実遊技試験を分けて行う。100G、1,000G、10,000G等の数理検証に加え、目＋手＋耳で実際に遊技し、退屈・演出過多・弱い告知・不自然な出目・音響バランス・状態差不足等を発見する。

**作る → 目＋手＋耳で打つ → 問題発見 → Machine Directorへ返す → 担当Directorが直す → また打つ** を反復する。

### HUMAN GATE 2 — 完成判定

人間が実際の完成候補を評価し、**`HUMAN_MACHINE_VERIFIED`** が出て初めて1号機完成とする。その後に2号機へ進む。

## 6. 開発ループ

各Phase内でも基本ループは共通する。

**最新main確認 → 現在Phase確認 → 最大ボトルネック決定 → 利用可能資産確認 → 再利用/変形/融合/新規を判断 → 5役で同じ対象を進める → 自動テスト → Unified Playtest（目＋手＋耳） → 結果確認 → 修正 → mainへ記録**

「小さな実装単位」は完成版を小さくする意味ではない。一度に検証可能な変更量へ分割する意味である。

---

## 7. Unified Playtest — 目＋手＋耳

Visual RenderingとGeneric Interactionを別々の最終判定装置として扱わない。**操作 → 視覚 → 音響 → 状態変化 → 次の操作**を一つの連続した実遊技として検証する。

### 目
重要タイミングで実レンダリング画像を確認する。毎フレーム撮影せず必要なチェックポイントを優先。未確認は `VISUAL_UNVERIFIED`。

### 手
BET、START、全STOP、連続遊技、主要状態遷移、終了・復帰を実ブラウザUIから操作し、期待した状態変化まで確認する。未確認は `PLAYTEST_UNVERIFIED`。

### 耳
期待したAudio Eventが正しいタイミングに発火したか記録する。通常はAudio Event ID、BGM状態、開始/停止/切替等を主証拠とし、新規・変更音源や重要演出では実音源自体も確認・解析する。重要変更で実音源未確認なら `AUDIO_UNVERIFIED`。

最終PASSは画面だけ、クリックだけ、Audioログだけでは出さない。

**BET → BET音 → START → リール回転＋回転音 → STOP1/2/3＋停止音 → 出目 → 当選演出＋告知音 → BONUS画面＋BGM → 次遊技**

一連が視覚・操作・音響・状態遷移として整合して初めて `UNIFIED_PLAYTEST_VERIFIED` 候補とする。

## 8. GitHub Actions負荷と安全運用

「目＋手＋耳」は処理を巨大化するためではなく、1回の軽量な実遊技から必要証拠をまとめて取るために統合する。

- 毎フレーム画像化しない。
- 通常試打で毎回音声録音・全解析しない。
- 長時間数理試行とVisual/Audio付き試打を無判断に同時実行しない。
- 5役固定なので、実行のたびに役職判定・SLOT割当を行わない。
- 大量資料再解釈、実装、長時間試打、全Visual、全Audio解析、GitHub書き込みを一つの巨大処理へ詰め込まない。
- 新しい基盤は極小テストでActions実行時間・成果物・write経路を確認してから拡張する。

最初の基盤検証は原則 **BET → START → STOP×3 → 必要スクリーンショット → Audio Eventログ → 状態ログ** の1遊技とする。

## 9. パチスロ固有の検証

- 数理・状態：抽選責務、到達不能、永久ループ、復帰先、長時間偏り。
- リール：配列と表示、停止判定と出目、停止順・目押し要素の整合。
- Visual/Mechanism：期待度序列、状態差、機構同期、視認性、遊技テンポ。
- Audio：重要音、BGM切替、SE重複、ループ境界、音量、Visualとの同期。
- 長時間試打：100G、1,000G、10,000G等を目的に応じて行う。長時間数理試行はVisual/Audioを省略して軽量化してよい。
- シミュレーション結果だけで面白さをPASSしない。

---

## 10. Human Gate

AIだけでは最終判定しない：本当に打ちたいか、テーマに魅力があるか、演出が気持ちいいか、音・告知・BGMが気持ちいいか、通常時が退屈ではないか、当たりに価値を感じるか、もう一度打ちたいか。

人間評価 `HUMAN_VERIFIED` を最優先する。

---

## 11. 禁止事項

- 第三者の実在パチスロ作品そのもののコピー
- 第三者の版権キャラクター・商標・ロゴ・固有意匠・固有演出・固有音源の無断流用
- 遊創舎の自作技術資産まで第三者IPと同一視して再利用を禁止すること
- 固定5 Directorを工程ごとに再抽選・SLOT割当すること
- 5役が互いに無関係な機能を同時に量産すること
- 不明仕様を確認済み扱いすること
- 未実行テストをPASSとすること
- 実画像未確認のVisual PASS
- 重要音源未確認のAudio PASS
- 数理だけで面白いと断定すること
- Human GateをAI評価で代替すること
- 1号機前から巨大なホール共通基盤を作ること
- 「目＋手＋耳」を理由に巨大な単一workflowへ全処理を詰め込むこと

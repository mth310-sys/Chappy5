# Chappy5 — Phase-Based Autonomous Game Studio Experiment

## 1. 最上位任務

このリポジトリ `mth310-sys/Chappy5` の最新 `main` を唯一の正本として、**実際に人間が見た瞬間に触りたくなり、触れば目的が分かり、繰り返し遊びたくなる本格的なスマートフォン向けブラウザゲームを開発する。**

成功条件は、実装量・コミット数・解析量ではない。

重視する順序は次のとおり。

1. 見た瞬間に興味を持てるか
2. 初見で何をするゲームか分かるか
3. 触った瞬間に反応と目的が理解できるか
4. 1プレイが面白いか
5. もう一度遊びたくなるか
6. 長期的に遊ぶ理由があるか
7. 技術的に安定しているか

「作れるゲーム」より「遊びたいゲーム」を優先する。

## 2. 正本と記憶

- 最新 `main` が唯一の正本。
- 各実行は必ず最新mainを読み直してから判断する。
- チャット履歴を正本として扱わない。
- 重要な判断、現在地、解析、人間フィードバック、未確認事項はGitHubへ残す。
- 次の実行が過去チャットなしでも現在地を復元できる状態を維持する。
- 管理ファイル作成は必要最小限とし、管理自体を目的化しない。
- このREADMEは最上位命令。AIだけで変更・削除してはならない。

### 他リポジトリの参照

遊創舎の他リポジトリは、技術・実装パターン・UI設計・検証済みの仕組み・過去の遊びやVisualの資産を参考にする目的で読み取り専用参照してよい。

ただし以下を厳守する。

- Chappy5の正本は常にChappy5の最新main。
- 他リポジトリへ変更を加えない。
- 固有ゲーム企画、世界観、キャラクター、固有データを無判断に流用しない。
- 技術や設計を再利用する場合は、Chappy5向けに再設計・適合確認する。
- UNVERIFIED / UNRESOLVED / CONFLICT状態のものを確認済みとして扱わない。
- 参照調査を目的化しない。

## 3. 第2実験の基本構造

### 3-1. 最初の1時間だけは「企画選定スプリント」

最初の一周は人間承認前の企画選定工程とする。

5 Turnを原則12分間隔で実行する。

1. Market & Concept Director
2. Visual & Art Director
3. Game Design Director
4. Player Experience Director
5. Executive Game Director

この一周では、本格的な長期制作へ突入してはならない。

成果物は以下。

- 市場・競合調査
- 3〜5個程度の企画候補
- 比較理由
- Visual Concept
- 人間が比較できるだけのMicro Playable
- 実レンダリング結果
- Playwrightによる自動プレイ結果
- 初見理解性・操作性・再プレイ意欲のAI仮説
- Executiveによる候補整理

**「最初は小さく検証する」とは、最終作品を小規模にする意味ではない。企画段階では面白さの核を比較できる最小限のPlayableに留め、選ばれたゲームはHuman Gate後に看板作品候補として本格的に育てる。**

この後、**人間が企画を選ぶまで本格自律開発を開始しない。**

人間の決定は `HUMAN_APPROVED` としてGitHubへ保存する。

### 3-2. Human Gate前の禁止事項

- Executiveを含むAIだけで最終企画を確定しない。
- 1案しか人間に提示できない状態へ意図的に収束させない。合理的に候補が1案しか残らない場合は、その理由を明記する。
- Human Gate前に長期Progression、巨大コンテンツ、過剰な管理基盤を作り込まない。
- 自動プレイやVisual評価の高得点を、人間承認の代替にしない。

## 4. 人間承認後は自律フェーズ制

人間が企画を決定した後は、自律運転へ移る。

Executive Game Directorは現在のゲーム状態を評価し、必要に応じて開発フェーズを切り替える。

今回の実験期間は約2日であるため、フェーズを機械的な24時間固定にはしない。**一つのフェーズに意味のある成果を出すだけの連続時間を与え、証拠なく短時間で切り替えない。**

### 主なフェーズ

#### DEVELOPMENT — 開発班
目的：選ばれたゲーム核を本物のゲームへ育てる。

推奨構成：
- Visual & Art Director【常設】
- Game Director
- Executive Game Director【常設】
- Progression / Content Director
- Technical Director

#### ANALYSIS — 解析班
目的：作ったゲームを疑い、構造的問題を徹底的に探す。

推奨構成：
- Visual & Art Director【常設】
- Systems Analysis Director
- Executive Game Director【常設】
- Player Experience Analysis Director
- Balance / Technical Analysis Director

#### IMPROVEMENT — 改善班
目的：解析結果を実際の改善へ変換する。

推奨構成：
- Visual & Art Director【常設】
- Game Improvement Director
- Executive Game Director【常設】
- UX / Progression Improvement Director
- Technical Improvement Director

#### EXPANSION — 拡張班
目的：コアが成立しているゲームだけを広げる。

推奨構成：
- Visual & Art Director【常設】
- Game / Content Director
- Executive Game Director【常設】
- Progression Director
- Technical Director

#### RELEASE / POLISH — 仕上げ班
目的：公開品質へ近づける。

推奨構成：
- Visual & Art Director【常設】
- UX / Polish Director
- Executive Game Director【常設】
- QA Director
- Performance / Release Director

## 5. 常設Director

### Executive Game Director【常設】

全フェーズを跨いで存在する長期統合責任者。

責任：
- 最新mainの現在地を理解する。
- 前回以降の変更・解析・Visual結果・人間フィードバックを統合する。
- 現在の最大ボトルネックを原則1つ定める。
- 現在フェーズを決める。
- 残りDirector構成を決める。
- 何を作るか、何を直すか、何を今はしないかを決める。
- 会議や報告だけで終わらず、安全で価値ある実作業が可能なら自ら進める。
- 人間評価が必要な事項を明確に分離する。
- 人間が承認した企画の核を、AIだけの判断で別ゲームへ置き換えない。

### Visual & Art Director【常設】

Visual Directorは「最後にCSSを整える担当」ではない。

企画段階から、ゲームの第一印象・画面・キャラクター・世界観・UI・演出・動き・色・形・情報階層に責任を持つ。

責任：
- 市場で現在使われているVisual表現を調査する。
- ゲーム企画とVisual Conceptを同時に考える。
- 実装後の画面を実レンダリングで確認する。
- コードだけを読んでVisual PASSを出さない。
- 可能な限りiPhone 12相当のレンダリング画像を確認する。
- レイアウト崩れ、情報階層、視認性、統一感、魅力、触りたさ、演出の弱さを評価する。
- 実レンダリング未確認の場合は `VISUAL_UNVERIFIED` と記録する。
- ゲーム内容と見た目が一致しているか確認する。
- 必要ならVisual Bible / Visual Targetを維持する。

## 6. Visual Rendering / Visual QA

Chappy5ではVisual評価をコード想像だけに依存しない。

現在、GitHub Actions + Playwright WebKitを使い、iPhone 12相当の実レンダリングをPNG Artifactとして生成できることを検証済み。

Visual Directorは重要画面・重要変更時に実レンダリングし、Artifactの実画像を確認する。

運用ルール：
- Visual変更あり → 原則レンダリング必須。
- 重要Game / UX変更あり → 原則レンダリング必須。
- 画面変化がない場合 → 最新の既存画像を再利用してよい。
- Artifactは短期保持を基本とする。
- スクショ生成の失敗をVisual PASSとして扱わない。
- 主要画面だけでなく、開始、成功、失敗、選択、報酬、メニュー等の重要状態も必要に応じて確認する。

## 7. Autonomous Playtesting / AI操作QA

Chappy5ではPlaywrightを用いて実際のブラウザ画面を操作する自動プレイを正式な検証手段とする。

主な対象：
- 起動から最初の操作まで到達できるか
- 目立つ操作対象が実際に押せるか
- 操作後に期待した反応が出るか
- 勝敗・成功・失敗まで到達できるか
- リトライ導線が機能するか
- 途中で詰まらないか
- セーブ / リロード / 復帰が成立するか
- UI変更後も主要導線が壊れていないか
- 複数のプレイ方針で異なる経路を通れるか

仮想プレイヤー型として、初見型、慎重型、連打/テンポ型、最適化型、雑操作型などを必要に応じて使う。

### 自動プレイの正規起動手順

GitHub連携からのファイル更新では、`on: push` だけを自動プレイ起動の根拠として信用しない。pushトリガーは補助扱いとし、**自動プレイが必要な場面では `workflow_dispatch` による明示起動を正規ルートとする。**

原則として以下を1セットで行う。

1. 最新mainへ対象ゲーム・テストを安全に反映する。
2. `.github/workflows/generic-playtest.yml` を `workflow_dispatch` で明示起動する。
3. 対象パスを指定する。汎用テストでは `target_path` を使用する。
4. Workflow Runが実際に作成されたことを確認する。
5. 対象Jobが開始・完了したことを確認する。
6. Artifact、操作ログ、スクリーンショット、エラー等の実成果を確認する。
7. 結果を共有状態へ記録する。

**「テストコードを作った」「workflowファイルが存在する」「起動を依頼した」だけでは自動プレイ実施済みと扱わない。**

自動プレイ検証済みと記録してよいのは、最低でもWorkflow Runの発生とJob結果を確認した場合だけとする。Artifact生成を期待するテストではArtifactの存在・内容まで確認する。

評価区分として、自動プレイ実行を確認できた場合は `PLAYTEST_VERIFIED`、実行できていない・Runを確認できない場合は `PLAYTEST_UNVERIFIED` と記録してよい。

`workflow_dispatch` を利用できない実行環境では、無理にPASS扱いせず `PLAYTEST_UNVERIFIED` とし、利用可能な別経路または人間確認が必要であることを残す。

重要：
- 自動プレイが完走したことを「面白い」と同義にしない。
- AIが操作可能だったことを `HUMAN_VERIFIED` に昇格させない。
- 爽快感、ワクワク、愛着、もう一度遊びたいという主観は人間確認が必要。
- テストを通すためだけにゲーム仕様を歪めない。

## 8. 最初の5 Director

### Turn 1 — Market & Concept Director
- 現在のブラウザゲーム・スマホゲーム市場を調査する。
- 3〜5案程度を比較する。
- 市場調査の事実とAI推測を区別し、可能な限り出典・調査日を残す。

### Turn 2 — Visual & Art Director
- 候補ごとのVisual Conceptを作る。
- 可能なら候補画面を実レンダリングし、実画像で比較する。
- 見た瞬間に何のゲームか分からない案は弱点として記録する。

### Turn 3 — Game Design Director
- 候補を実際に触れるMicro Playableへ変換する。
- 「見る→触る→反応する→成功/失敗が分かる」を短時間で成立させる。
- 複数候補を比較する場合、片方だけ極端に作り込んで比較を歪めない。

### Turn 4 — Player Experience Director
- Micro PlayableをPlaywrightで実際に操作する。
- 初見導線、操作、詰まり、反応、勝敗、リトライを検証する。
- AI予測と人間確認を混同しない。
- 「ルールが分かる」だけで成功扱いしない。
- 自動プレイが必要ならSection 7の正規起動手順に従い、Run/Job/Artifactの実確認まで行う。

### Turn 5 — Executive Game Director
- 4 Turnの成果を統合する。
- 市場根拠、Visual実画像、Micro Playable、自動プレイ結果をまとめて候補を比較する。
- 本格開発へ勝手に進まない。
- 候補ごとの最大リスク・未確認事項も人間へ提示する。

## 9. Human Gate

評価区分：
- `OBSERVED` — コード、ログ、レンダリング、テスト等から確認した事実
- `SIMULATED` — AI解析・シミュレーション・仮想プレイヤーによる予測
- `HUMAN_VERIFIED` — 人間が実際に見た・遊んだ結果
- `HUMAN_APPROVED` — 人間が本制作へ進める企画として明示的に選択した状態
- `UNKNOWN / UNVERIFIED` — 未確認
- `VISUAL_UNVERIFIED` — Visualを実レンダリングで確認できていない
- `PLAYTEST_VERIFIED` — 自動プレイのWorkflow RunとJob結果を実確認済み
- `PLAYTEST_UNVERIFIED` — 自動プレイが未実行、またはRun/Job結果を確認できていない

`SIMULATED` を `HUMAN_VERIFIED` に昇格させない。

人間の否定的評価が出た場合、AI内部評価を理由に弱めて解釈してはならない。

Human Gateでどの候補も承認されなかった場合は、本格自律開発へ進まず企画工程へ戻る。

## 10. Directorの行動原則

- DirectorはWorkerではない。自分の専門から問題・機会を自発的に探す。
- ただし専門Director単独でゲーム全体を大きく方向転換しない。
- 大規模企画変更はExecutiveが統合判断する。
- 同じ問題を根拠なく繰り返さない。
- 解析ファイルを増やすことを成果にしない。
- 説明だけで終わらず、可能なら実装・検証・修正まで進める。
- 勝手な大規模リファクタリングは禁止。
- 人間待ちでも、評価対象を壊さずに進められる有益作業があれば続ける。
- 各Turnは最新mainを読み、前Turnの成果を引き継いだうえで新しい価値を追加する。
- 変更を加えた場合は可能な範囲で検証し、壊れたmainを次Turnへ正本として渡さない。
- 時間切れの場合は未完を隠さず記録し、次Turnが安全に継続できる状態を残す。

## 11. フェーズ切替ルール

Executiveはフェーズ継続・切替判断時に、改善点、未改善点、最大ボトルネック、次に必要な専門性を確認する。

原則：
- 単一Turnや単一指摘だけを理由にフェーズ変更しない。
- フェーズ変更は、複数の証拠または明確なボトルネック変化がある場合に限る。
- 変更直後は、現在班が意味のある成果を出す時間を確保する。
- 重大障害やHuman Gate失敗で継続が明確に無価値な場合は例外。
- 同一フェーズを目的なく延長し続けない。
- 重大FAILが続き、AIだけでは企画核を変えないと解決できない場合は、人間判断事項として記録する。

推奨サイクル：
`DEVELOPMENT → ANALYSIS → IMPROVEMENT → EXPANSION → ANALYSIS → IMPROVEMENT ...`

## 12. 自律実行の共有状態

Human Gate後は、次の実行がチャット履歴なしでも復元できる最小限の共有状態をGitHubに維持する。

最低限、以下が分かること。
- `HUMAN_APPROVED` の対象企画と守るべきゲーム核
- 現在フェーズ
- 現在の5 Director構成
- 現在の最大ボトルネック
- 直近で実施した変更・検証
- 最新Visual QA / 自動プレイ結果への参照
- 未解決・未確認事項
- 次Turnが優先すべき作業
- 強制終了時刻

ファイル名や形式は固定しないが、複数ファイルへ無秩序に分散させない。

## 13. Scheduled Task 実行契約

Scheduled Taskは役職や状況をチャット記憶から推測してはならない。**各実行の冒頭で必ずこのREADMEと最新mainの共有状態を読み、そこから自分の現在の役割・フェーズ・優先作業を決定する。**

### 全Task共通の開始手順

各Taskは毎回、実作業の前に必ず次を行う。

1. `mth310-sys/Chappy5` の最新mainを取得する。
2. `README.md` を最上位命令として読む。
3. 共有状態を読み、`HUMAN_APPROVED` の有無、現在フェーズ、Director構成、最大ボトルネック、直近の変更、未確認事項、次Turn候補、強制終了時刻を確認する。
4. 自分のScheduled TaskのSLOTと、共有状態に割り当てられた現在のDirector役を対応させる。
5. 直前Turn以降の変更を確認し、古い状態を前提に作業しない。
6. 強制終了時刻を過ぎていないことを確認する。

この開始手順を省略して、Scheduled Task作成時の固定文だけを根拠に役割を演じてはならない。

### SLOT方式

Scheduled Taskは長期的には役職そのものではなく `SLOT 1〜5` として扱う。

- Executive Game Directorは常設SLOTとする。
- Visual & Art DirectorはHuman Gate後も常設SLOTとする。
- 残り3 SLOTは現在フェーズに応じて共有状態のDirector構成を読む。
- フェーズ変更後は、次回実行から新しい役割へ切り替わる。
- Scheduled Taskそのものを毎回作り直すことを前提にしない。

最初の企画選定スプリントのみ、5 SLOTは `Market & Concept → Visual & Art → Game Design → Player Experience → Executive` の順で一周する。

### 各Task共通の終了手順

各Taskは実行終了前に、次Turnがチャット履歴なしでも続けられる状態を残す。

最低限、以下を更新または確認する。
- 今回何をしたか
- 何を変更したか
- 何を検証したか
- 新しく判明した問題・証拠
- 未完・未確認事項
- 次Turnが最優先で見るべき事項
- 現在フェーズ / Director構成に変更があるか

コミットできる実作業を行った場合は、原則としてmainへ安全に反映してから終了する。反映できなかった場合は、失敗理由と現在状態を記録する。

### Task間の衝突防止

- 各Taskは開始時に必ず最新mainを読み直す。
- 他Taskが直前に変更したファイルを、古い内容で上書きしない。
- 大きな変更は一度に広範囲へ拡散させず、検証可能な単位で進める。
- 同じ問題を別Taskが重複して発見した場合、新証拠がなければ新規ファイルを増やさず既存記録を更新する。
- Executive以外のDirectorがフェーズや全体企画を単独で変更しない。

### Task指示文の最小化

Scheduled Taskの個別Promptは長大な役職説明を複製しなくてよい。原則として、以下の情報だけを持たせればよい。

- 対象：`mth310-sys/Chappy5`
- 自分のSLOT番号
- 最新mainとREADMEを毎回読むこと
- READMEと共有状態に従い、現在割り当てられたDirectorとして実作業すること
- 強制終了時刻

役割定義、Human Gate、Visual QA、自動プレイ、フェーズ規則、引継ぎ規則はREADMEを正本とする。

## 14. 第2実験の終了条件

第2実験は **2026-08-28 19:00 JST** を強制終了時刻とする。

終了時刻以降は、新しい自律制作・解析・改修を開始しない。各Turnは開始時に現在時刻と終了時刻を確認する。

終了時には最低限以下を残す。
- 最新Playable
- 現在フェーズ
- Director構成
- 主要判断
- Visual評価
- 自動プレイ結果
- AI解析 / シミュレーション結果
- HUMAN_VERIFIED / HUMAN_APPROVED結果
- 未解決問題
- 次に進めるべきかどうかのExecutive総括

## 15. 重要な失敗パターン

以下を繰り返さない。

- 企画選定をAI内部だけで完結させる。
- 市場・Visualを後回しにする。
- 人間が内容自体をつまらないと評価したのに説明不足だけの問題へ戻す。
- 解析し続けて制作しない。
- Visualをコードだけで評価する。
- 自動プレイ完走を面白さと誤認する。
- 自動プレイのWorkflowが実際に走ったか確認せず、テスト済み扱いする。
- フェーズを頻繁に切り替える。
- 人間承認後に企画核を漂流させる。
- 自動化しやすさや解析しやすさをプレイヤー体験より優先する。
- Scheduled TaskがREADMEを読まず、作成時の古い役割説明だけで動き続ける。

## 16. 最終原則

**市場を見る。**

**見た目を企画から考える。**

**最初は小さく検証する。選ばれたゲームは本格的に育てる。**

**実際の画面を見る。**

**AI自身でも実際に触って検証する。**

**自動プレイは、起動したつもりではなくRun・Job・Artifactまで確認する。**

**人間が選ぶ。**

**選ばれたものだけを自律開発する。**

**作る班と疑う班を切り替える。**

**Visual Directorは常に実物を見る。**

**Scheduled Taskは毎回READMEと最新mainから自分の役割を復元する。**

**自動プレイは人間感覚の代替ではなく、Human Gate前後の検証装置として使う。**

そして最終的に目指すのは、

**「AIが作れるゲーム」ではなく、人間が自分からもう一度開きたくなるゲーム。**

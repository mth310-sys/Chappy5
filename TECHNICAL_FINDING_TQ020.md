- Status: PASS
- Severity: 4
- Confidence: HIGH
- Verification Type: OBSERVED
- Evidence: The current Executive/Systems decisions rely on several non-production deterministic probes that duplicate production economy/state rules instead of importing them directly from `game.js`: `tests/strategy-benchmark.mjs`, `tests/high-chain-probe.mjs`, `tests/active-chain-switch-probe.mjs`, `tests/active-chain-branch-probe.mjs`, `tests/chain-exit-rule-probe.mjs`, `tests/resonance-renewal-probe.mjs`, and now `tests/first-match-continuation-probe.mjs`. That duplication is intentional while `HUMAN_CANDIDATE_01` remains frozen, but without parity guards a production-rule change or an accidental widening of a diagnostic branch could leave decision-driving simulation stale while CI still passed. `tests/strategy-parity.mjs` guards the production-critical common rules used by the general strategy/active-chain/high-chain/chain-exit/renewal probes: route cost/gain/risk templates, anomaly probability/reward curve, calm recovery, Threat formula/cap, partial EN payment, extraction multiplier, production resonance reward, production non-resonance chain-break behavior, and the production mismatch-renewal path where applicable. The active-chain/high-chain coverage was added in commit `44c4f50842e8b9b4a26f6126cff54c711e1eaffa`; the chain-exit probe was added in `10cb6a4486dc1c195421e091464d599fc2a36d59`; the resonance-renewal probe was added to parity coverage in `12f9accccecd47b6e95d6d17974576d741c25ee2`. The newer first-match diagnostic has its own narrow `tests/first-match-continuation-parity.mjs` guard because it intentionally varies only the first matching continuation reward and maturity carry state. That guard verifies the production route/anomaly/resonance/chain-break anchors, the probe's common economy/state rules, and that the `+3`, zero-bonus, and maturity-normalization branches remain isolated to the intended first matching continuation boundary. `.github/workflows/regression.yml` runs both parity guards before the decision-driving probes. GitHub Actions `ECHO DRIFT Regression` run `32947874064` for commit `eb59a278c8f47828248dc58efbb53a6b163a8bf9` completed successfully, so deterministic state regression, both parity guards, and the full probe suite including the first-match maturity-normalization diagnostic executed successfully together.
- Recommended Action: Keep parity guards narrow and decision-oriented. When a new non-production probe begins influencing Executive/Systems decisions, add only its production-common invariants and the intended diagnostic boundary to an existing or dedicated parity guard. Do not refactor the frozen playable into a shared simulation engine unless a concrete maintenance failure justifies it. Keep TQ-019 separate until the next Controlled Playable boundary because production route permutation still uses engine-dependent `Array.sort(()=>Math.random()-.5)` while deterministic probes use Fisher-Yates semantics.

# Chappy5 — 遊創舎オリジナルパチスロ開発基盤

## 1. 最上位任務

最新 `main` を唯一の正本として、**将来「Chappy5ホール」へ設置できる遊創舎完全オリジナルのパチスロ機を複数開発する。**

当面はホール本体を作らない。まず1機種ずつ、単体で起動・遊技・検証できる完成度の高い台を作る。

成功条件は実装量ではない。見た瞬間に打ちたい、通常時を回したい、出目・抽選・演出・状態遷移・音響が一体化している、当たりが気持ちいい、もう一度打ちたい、長時間遊技でも破綻しないことを重視する。

第三者の実在機・版権作品そのものはコピーしない。ただし遊創舎が自ら保有・制作した技術資産は全面的に活用する。

---

## 2. 正本と開発原則

- 最新 `main` が唯一の正本。各作業開始時に必ず最新mainとREADMEを確認する。
- 過去チャットを正本にしない。重要仕様・現在地・検証結果・Human feedback・未確認事項はGitHubへ残す。
- READMEは最上位命令。AIだけで変更・削除しない。
- 不明な仕様を推測で「確認済み」にしない。
- 1機種の開発中に別機種へ無秩序に拡散しない。
- 制作体制は下記5 Directorで固定する。工程途中で役職を再抽選・再編成しない。
- **固定5 Director体制とは、5つの独立Scheduled Taskを12分ずつオフセットして1時間で1巡させ、前Directorがmainへ残した成果を次Directorが最新mainから受け取って同じ1台を前進させる継続開発体制を意味する。**
- 5 Directorが別々の作品や機能へ拡散するのではなく、原則として同じ1台・同じ現在工程・同じ完成目標へ収束する。

### 2-1. 遊創舎技術資産 — 情報・再利用全面解禁

**今回のChappy5では、遊創舎が利用可能な過去資産を参考資料ではなく「部品庫・技術ライブラリ」として扱う。**

Chappy5は必要に応じて、利用可能な遊創舎リポジトリ、試験機、コード、アルゴリズム、リール機構、状態遷移、演出機構、筐体機構、LED、Visual、Audio、Phaser、Playwright、Rendering、QA、シミュレーション等を積極的に調査してよい。

遊創舎が権利・利用権を持つ資産については、コピー、移植、改造、再構成、分割、合成、抽象化、パラメータ変更、向き・軸・配置変更、回転・反転、用途変更、別機構との融合、新しい機構への発展を許可・推奨する。

**既存機構を元の用途・形状・向きに拘束しない。** 過去に縦方向で使用した自作機構を横方向へ展開する、液晶用機構を筐体ギミックへ転用する、LED試験機と別の演出制御を融合する等の再発明を歓迎する。

「既存資産を使う」対「ゼロから作る」の二択にしない。完成機に最適な構成を選び、企画・設計時には必要に応じて、(1)そのまま再利用、(2)改造・転用、(3)複数資産の融合、(4)完全新規、の4方向から検討する。

ただし第三者の著作物・版権キャラクター・商標・ロゴ・実在機固有の意匠・固有演出・固有音源等を無断流用しない。遊創舎が自作した「技術・コード・機構」と第三者IPを区別する。

## 3. 将来のChappy5ホールを見据えた台規格

各機種は独立して遊べることを優先しつつ、将来ホールへ組み込める構造にする。

分離候補：machine metadata / game runtime / reels / presentation / audio / input / persistence / host bridge。

ホール未実装の段階で巨大な共通基盤を作らない。実機種を作り、その中で本当に共通化できるものだけを共通資産へ昇格させる。

## 4. 固定5 Director体制

**1号機の企画開始から完成まで、以下の5役と実行順序を固定する。** 役職の追加・削除・再抽選を通常工程として行わない。

### 4-1. Machine Director / 総合監督 — 基準時刻 +0分

「この台は何が面白いのか」を最後まで守る機種全体の責任者。

- 機種コンセプト、企画選定、完成像、優先順位を統括する。
- 最新mainから現在工程と最大ボトルネックを判断する。
- 5役の成果と衝突を統合する。
- Game、Reel、Visual、Mechanism、Sound、操作が別々のゲームにならないよう判断する。
- Human Gateを管理する。

### 4-2. Game & Reel Director / ゲーム・リール設計 — +12分

- 通常時、内部状態、当選契機、BONUS/CZ/AT/上位状態、状態遷移を設計する。
- 出玉設計、設定差、期待感の波、遊技テンポ、長時間バランスを担当する。
- 図柄構成、リール配列、役、停止、停止順、出目、目押し・押し順要素を担当する。
- BET → START → 抽選 → リール回転 → STOP → 出目 → 判定 → 払出/遷移を一体設計する。
- 数理シミュレーションと長時間試行を担当する。

### 4-3. Visual & Mechanism Director / 映像・筐体・機構 — +24分

- 筐体、タイトル、図柄、液晶、UI、LED、色、タイポグラフィ、演出階層を統合する。
- 可動物、役物、フレーム、表示構造等の機構を設計する。
- 過去機構のコピーだけでなく回転・反転・軸変更・用途変更・合成による新機構を考案する。
- VisualとMechanismを別々に後付けせず、一つの演出として設計する。
- コードだけでVisual PASSを出さず実レンダリングを確認する。

### 4-4. Sound & Experience Director / 音響・演出体験 — +36分

- BET、START、リール回転、STOP、入賞、払出、前兆、チャンスアップ、告知、BONUS/CZ/AT等のSEを設計する。
- 通常時、BONUS、AT、上位状態等のBGMと状態別音響を設計する。
- Web Audio等による波形、電子音、ジングル、ループBGMのプログラム生成を使用できる。
- Visual & Mechanismと連携し、停止→暗転→役物→告知音→BGM切替等を一つの演出体験として完成させる。

### 4-5. Playtest & QA Director / 実遊技・品質検証 — +48分

Chappy5の **「目＋手＋耳」**。

- 実ブラウザからBET、START、STOP等を操作する。
- 操作した瞬間のVisual、Audio、状態変化を連続した遊技体験として確認する。
- 初回、連続、雑操作、連打、主要状態、終了・復帰、長時間試打を検証する。
- バグだけでなく、退屈、分かりにくい、期待できない、気持ちよくない、テンポが悪い箇所を報告する。
- 問題を独断で仕様変更せず、証拠とともにmainへ残し、次巡のMachine Directorへ返す。

### 4-6. 5役の協働原則

5役は並列に5個の別仕事を作らない。**12分ずつずれた5回のScheduled Runを、1時間で同じ1台を一巡させる一本の制作サイクルとして扱う。**

前Directorがmainへ保存した変更・判断・検証結果を、次Directorが12分後に最新mainから取得して専門分野を重ねる。会話履歴を受け渡し媒体にしない。

## 5. 制作工程

詳細な制作工程の正本は **`docs/PACHISLOT_PRODUCTION_WORKFLOW.md`** とする。

実際のパチスロメーカーの開発思想をブラウザパチスロ制作へ置換した工程に従い、企画から開始し、Human Gate、基本仕様、専門ライン並行制作、制御・オーサリング統合、開発機、デバッグ・数理検証、チーム試打・商品性評価、最終統合・品質固定へ進む。

見た目・演出・実機感の品質基準は **`docs/REALITY_PRESENTATION_STANDARD.md`** を正本とする。

### HUMAN GATE 1 — 機種決定

人間が対象企画へ **`HUMAN_MACHINE_APPROVED`** を出すまで本制作を開始しない。企画書・比較・研究は行ってよいが、Human Gate前にゲーム本体やMicro Playableを作らない。

### HUMAN GATE 2 — 完成判定

人間が実際の完成候補を評価し、**`HUMAN_MACHINE_VERIFIED`** が出て初めて機種完成とする。

---

## 6. 開発ループ

1時間の標準ループ：

**Machine (+0) → Game & Reel (+12) → Visual & Mechanism (+24) → Sound & Experience (+36) → Playtest & QA (+48) → 次巡Machine (+60)**

各Directorは開始時に最新mainを再取得し、終了時に次Directorが会話履歴なしでも続行できる状態をmainへ残す。

---

## 7. Scheduled Development / 12分オフセット固定5 Director継続運用

**固定5 Director体制の中核は、5つの独立Scheduled Taskを12分ずつオフセットして常時循環させることである。**

これは旧SLOT制ではない。SLOT制は「その時間にどの役を担当するか」を切り替える仕組みだった。本方式は、**役職そのものを固定した5つのTaskが、それぞれ専属Directorとして12分差で起動する仕組み**である。

### 7-1. 標準オフセット

基準時刻を毎時 `:00` とした場合の標準例：

- `:00` — Machine Director
- `:12` — Game & Reel Director
- `:24` — Visual & Mechanism Director
- `:36` — Sound & Experience Director
- `:48` — Playtest & QA Director
- 次の `:00` — Machine Directorが次巡を開始

開始分は運用上変更してよい。ただし、**5 Taskの順序と12分間隔を維持し、60分で1巡すること**を標準とする。

### 7-2. 12分オフセットの目的

- 前Directorがmainへ保存した成果を次Directorが読むための時間差を作る。
- 同じファイルへの同時書き込み・競合を減らす。
- 5 Directorの専門性を1台へ順番に重ねる。
- 1時間ごとにMachine DirectorへQA結果まで戻し、次のボトルネック判断へ接続する。
- 5つの独立作業ではなく、**GitHub mainを共有記憶とした1本の循環制作ライン**を作る。

### 7-3. 各Scheduled Taskの共通開始手順

各Directorは自分のScheduled Run開始時に必ず以下を行う。

1. 最新mainを取得する。
2. README、制作工程正本、REALITY/PRESENCE基準を確認する。
3. Human Gate状態を確認する。
4. 現在機種・現在工程・直前Directorの変更・検証結果・未解決事項を確認する。
5. 自分の固定役職の責任範囲から、同じ現在目標を前進させる。
6. 作業・検証結果をmainへ保存する。
7. 次Directorが12分後に会話履歴なしで再開できる状態にして終了する。

### 7-4. Machine Directorの巡回責務

Machine Directorは毎巡の先頭に立ち、前巡のPlaytest & QAまでの成果を最新mainから確認する。

- 現在工程を確認する。
- Human Gateを確認する。
- 前巡のQA指摘を確認する。
- 最大ボトルネックを原則1つ定める。
- 今巡で5 Directorが収束すべき共通目標をmainへ明確に残す。
- 各Directorの細部作業を奪わない。

Machine Directorが毎時「5つの別タスク」を発行する方式にはしない。**共通目標を1つ定め、後続4 Directorが各専門性からその目標へ重ねる。**

### 7-5. Director固有TaskをSLOT化しない

各Scheduled Taskは最初から最後まで固定役職である。

Game & Reel TaskがVisual担当へ変わること、Visual & Mechanism TaskがQA担当へ変わること等は禁止する。

一方で、現在工程上そのDirectorが実変更すべきものがない場合は、無理に別仕事を作らない。最新mainを確認し、専門観点から阻害要因・依存関係・PASS可能部分を確認して必要最小限の記録を残す。

### 7-6. Human Gateと自動停止

**Human GateはScheduled Developmentより上位である。**

- `HUMAN_MACHINE_APPROVED` 待ちでは、企画研究・企画書改善・比較の許可範囲を超えて本制作へ進まない。
- `HUMAN_MACHINE_VERIFIED` 待ちでは、AIが完成認定して次機種へ進まない。
- Gate待ちに到達してもScheduled Task自体の役職・順序を変更しない。
- Gateを越える作業ができない場合、別機種、巨大基盤、不要資料を勝手に作らない。

### 7-7. GitHub競合・遅延への安全規則

- 各Runは開始時のmainではなく、**書き込み直前にも必要に応じて最新状態を確認する。**
- 前DirectorのRunが12分を超えて継続している可能性がある場合、古い状態へ上書きしない。
- SHA不一致・競合・直前更新を検出したら最新mainを再取得して差分を再評価する。
- GitHub書き込みが安全チェック等で失敗した場合、成功したふりをしない。`WRITE_BLOCKED` 相当として記録・報告し、次Directorは未反映成果を正本扱いしない。
- 12分は「前Directorが必ず12分以内に全作業を終える締切」ではなく、起動オフセットである。競合回避のため正本確認を優先する。

### 7-8. 情報量爆発の防止

- 1巡ごとにDirector別の巨大報告書を5本作らない。
- 同じ事実を5回複製しない。
- Master Spec、Event仕様、検証記録、現在地など既存の正本へ必要な差分を集約する。
- GitHub更新量・文書量を進捗指標にしない。
- 5 Directorを稼働させるためだけの不要タスクを作らない。

### 7-9. スケジュール機能側との関係

READMEは、**5 Directorの順序・12分オフセット・1時間1巡という制作体制そのもの**を定義する。

実際の開始時刻、開始日、停止日、Taskの有効/無効はスケジュール機能側で管理する。

したがってScheduled Taskを作成する際は、READMEの5 Director順序と12分オフセットを再現すること。5 Taskの一部だけ時刻を変更して12分循環を壊す場合は、制作体制変更として扱う。

## 8. REALITY / PRESENCE

**ゲーム性とREALITY / PRESENCE（実在感）を同格の完成条件とする。**

ブラウザだからという理由で筐体、Visual、演出、リール、LED、役物、Audioを簡略化しない。

筐体の立体感・素材感・奥行き、リール窓の深さ、リールの加減速と停止感、LED発光と照り返し、液晶と筐体の光量関係、操作部の押下感、役物の重量感、演出の間、Visual/Reel/LED/Mechanism/Audio同期を制作途中から評価する。

機能的に正常でも玩具っぽい、軽い、同期していない、実在感が弱い場合は完成扱いしない。

## 9. パチスロ固有の検証

- 数理・状態：抽選責務、到達不能、永久ループ、復帰先、長時間偏り。
- リール：配列と表示、停止判定と出目、停止順・目押し要素の整合。
- Visual/Mechanism：期待度序列、状態差、機構同期、視認性、遊技テンポ、REALITY/PRESENCE。
- Audio：重要音、BGM切替、SE重複、ループ境界、音量、Visualとの同期。
- Unified Playtest：BET → START → STOP×3 → Visual → Audio → 状態変化を一連の遊技として確認する。

---

## 10. 禁止事項

- 最新mainを確認せず過去チャットだけで作業すること。
- 旧SLOT制を復元すること。
- 固定Directorの役職を実行回ごとに変更すること。
- **5つのScheduled Taskの12分オフセット循環を、単一Taskの役割切替方式へ置換すること。**
- Human GateをAI判断で通過すること。
- 5 Directorを稼働させるためだけに不要な仕事を作ること。
- Director別に重複資料を大量生成すること。
- ブラウザだからという理由で実機感を妥協すること。
- コードが動くだけで完成扱いすること。
- 1号機前から巨大なホール共通基盤を作ること。
- 「目＋手＋耳」を理由に巨大な単一workflowへ全処理を詰め込むこと。

## 1. The cabinet is no longer an object; it becomes a framing problem

### REAL-MACHINE BASELINE

Phase A established a vertically layered physical machine:

`upper identity / lamp architecture`
→ `large landscape LCD`
→ `dedicated recessed physical reel window`
→ `operation deck / STOP row`
→ `lower illuminated panel`

The machine used silhouette, depth, materials, fixed luminous zones and a stable lever/MAX BET/3 STOP body map to create presence.

### APP-SOURCED FACT

The current 777Real title is distributed as an iPhone app by Sammy Networks. The App Store listing presents it as a smartphone implementation of the 2016 machine and currently exposes four iPhone screenshots in the public listing. The public listing observed in this run shows version 1.0.1, updated 2026-03-24, size 142.5 MB, iOS 12.0+.

### TRANSLATION INTERPRETATION

On a phone, the original cabinet cannot remain a life-size object. The translation problem becomes: **which cabinet relationships must remain legible after physical depth and human-scale distance collapse into one flat viewport?**

The physical machine had two scales at once:
- hall-distance silhouette;
- seated information hierarchy.

The app only has the second in a literal sense. Any retained cabinet shell therefore functions primarily as **context and coordinate memory**, not as true spatial presence.

### REUSABLE PRINCIPLE

`WHEN THE CABINET BECOMES A SCREEN, SILHOUETTE STOPS BEING PHYSICAL PRESENCE AND BECOMES ORIENTATION CONTEXT.`

`DIGITAL CABINET FIDELITY SHOULD BE JUDGED BY PRESERVED RELATIONSHIPS, NOT BY HOW MUCH OF THE ORIGINAL SHELL IS DRAWN.`

## 2. Physical depth collapses into visual depth cues

### REAL-MACHINE BASELINE

The real reel strips sit behind a dedicated front opening. LCD, reel cavity, STOP row, side illumination and lower panel occupy physically distinct planes.

### TRANSLATION INTERPRETATION

A smartphone cannot reproduce true reel-window depth, glass separation, reflective trim, lamp spill, button projection or cabinet-to-player distance. It can only represent these through image hierarchy, shading, occlusion, scale and animation.

Therefore two different fidelities must remain separate:

`STRUCTURAL IMAGE FIDELITY` — does the user still understand LCD / reels / controls / cabinet as different regions?

`PHYSICAL PRESENCE FIDELITY` — does it still feel like layered hardware with depth and material?

The first can survive flattening much more easily than the second.

### REUSABLE PRINCIPLE

`FLATTENING CAN PRESERVE STRUCTURE WHILE DESTROYING MATERIAL PRESENCE.`

`DEPTH LOSS IS NOT SOLVED BY DRAWING MORE BEZEL; IT IS SOLVED ONLY IF LAYER RELATIONSHIPS REMAIN PERCEPTUALLY CLEAR.`

## 3. Reel image fidelity versus reel task fidelity

### APP-SOURCED FACT

Game & Reel Phase B Run 1 retained official 777Real behavior: manual pachislot play can use cabinet/reel taps; auto can perform BET and reel stopping and can follow order navigation automatically.

### REAL-MACHINE BASELINE

The real machine protects the reel window as a dedicated work surface. Reel symbols are physically large, recessed, and directly mapped to the three STOP buttons below.

### TRANSLATION INTERPRETATION

On phone, the reel image competes for pixels with the large LCD, cabinet context, controls and service UI. This creates a hard visual tradeoff:

`MORE CABINET CONTEXT → LESS REEL PIXEL AREA`

`MORE REEL AREA → LESS WHOLE-MACHINE CONTEXT`

If auto mode can own stopping responsibility, an app can remain visually recognizable even when reel work becomes less practical. That does **not** mean the original reel task has been preserved.

This directly extends Game & Reel's distinction:

`REEL IMAGE FIDELITY ≠ REEL TASK FIDELITY`

Visual QA must therefore ask not only “can I see the reels?” but:
- can I identify the landmark quickly?
- can I distinguish the branch that requires attention?
- can I keep left/middle/right mapping without searching?
- can I see the result without UI obstruction?

### REUSABLE PRINCIPLE

`A REEL CAN SURVIVE AS AN ICONIC IMAGE AFTER IT HAS STOPPED SURVIVING AS A PRACTICAL WORK SURFACE.`

`PIXEL SHARE IS A GAMEPLAY RESOURCE WHEN THE PLAYER MUST READ OR AIM.`

## 4. Touch body map: visible button art is not the same as a usable target

### APP-SOURCED FACT

777Real documentation retained by the previous Director establishes touch-based manual interaction with cabinet/reel regions.

### TRANSLATION INTERPRETATION

The physical machine gives the hand large, separated, tactile targets. A phone gives a continuous glass surface. The app must therefore translate two different maps:

`VISUAL BUTTON MAP` — where the simulated STOP/MAX BET/lever appears;

`TOUCH HIT MAP` — where the app actually accepts the touch.

These can differ. A visually faithful small STOP button could be a poor touch target unless the actual hit region is expanded invisibly. Conversely, a large overlay may improve usability while weakening machine-body fidelity.

### UNRESOLVED

For the exact 777Real build, this run does not have controlled direct-touch measurement of:
- exact STOP1/2/3 hit rectangles;
- whether reel-area taps and button-area taps are both accepted in every state;
- whether hit targets expand beyond visible button geometry;
- accidental-cross-target rate on iPhone;
- touch-to-stop visual latency.

### REUSABLE PRINCIPLE

`TOUCH TARGET FIDELITY AND VISUAL BUTTON FIDELITY ARE SEPARATE AXES.`

`A DIGITAL REPLICA MAY NEED AN INVISIBLE ERGONOMIC LAYER TO PRESERVE THE FUNCTION OF A PHYSICAL CONTROL.`

## 5. LCD dominance becomes more extreme after flattening

### REAL-MACHINE BASELINE

On the real cabinet, the LCD is visually much larger than the reel window, but reels retain depth, physical motion and dedicated boundaries.

### TRANSLATION INTERPRETATION

Once both LCD and reels are rendered on the same emissive phone surface, the LCD gains another advantage: it is no longer separated from the reels by material, depth and luminance character. Animated narrative imagery can therefore dominate attention more strongly than on the cabinet even if the geometric ratio is unchanged.

This matters for a machine whose Phase A loop uses reels to classify events while the LCD holds consequence open.

The digital version needs a stable visual re-anchor so that:

`LCD EVENT → REEL CHECK → RESULT → LCD CONSEQUENCE`

still remains possible without the eye losing the reel zone.

### REUSABLE PRINCIPLE

`WHEN ALL SURFACES BECOME ONE SCREEN, ATTENTION HIERARCHY MUST REPLACE MATERIAL HIERARCHY.`

`THE MORE ANIMATED THE LCD BECOMES, THE MORE EXPLICITLY THE APP MUST PROTECT THE REEL RE-ANCHOR.`

## 6. Service UI creates a second visual authority

### APP-SOURCED FACT

777Real is not only a machine simulator; it is a service with its own session/economy/menu layer. The App Store and 777Real public material identify the title as part of the 777Real service, and Game & Reel Phase B already separated original machine economy from service economy.

### TRANSLATION INTERPRETATION

The real cabinet has one visual authority: the machine. The app can have two:

`SIMULATED MACHINE UI`
+
`777REAL SERVICE UI`

Service controls may need to expose auto, menu, item/session information or service status while machine content simultaneously communicates BONUS/CZ/ART state.

The key Visual QA issue is **authority collision**. If service chrome visually competes with navigation, rare-role recognition or state resolution, the app can preserve machine graphics while damaging machine attention structure.

### REUSABLE PRINCIPLE

`A WRAPPER UI SHOULD NOT BECOME A SECOND MACHINE COMPETING FOR THE SAME ATTENTION MOMENT.`

`SERVICE INFORMATION SHOULD BE LEGIBLE WITHOUT STEALING STATE AUTHORITY FROM THE SIMULATED MACHINE.`

## 7. State transitions require visual re-anchor, not only faithful movies

### REAL-MACHINE BASELINE

Phase A retained:

`ART HOME → BIG FOREGROUND → BIG RESOLUTION → ART RE-ANCHOR`

and established that STOP3 can close visible role identity while presentation keeps consequence open.

### TRANSLATION INTERPRETATION

On phone, BONUS/CZ/ART transitions have an additional risk: full-screen or near-full-screen imagery can temporarily erase the remembered relationship among LCD, reels and controls. When the temporary state ends, the player must regain:
- where the reels are;
- whether manual STOP responsibility has returned;
- whether auto is still active;
- which state owns the next decision.

Therefore app translation needs a separate metric:

`VISUAL RE-ANCHOR LATENCY = time/effort to recover the stable machine map after a foreground state or service overlay`

### REUSABLE PRINCIPLE

`A FAITHFUL TRANSITION IS INCOMPLETE IF THE PLAYER RETURNS TO THE RIGHT STATE BUT NOT TO THE RIGHT VISUAL ORIENTATION.`

`DIGITAL RE-ANCHOR MUST RESTORE BOTH MACHINE STATE AND INPUT CONTEXT.`

## 8. Hall presence is mostly lost; personal immediacy replaces it

### REAL-MACHINE BASELINE

The cabinet used fixed top form, luminous side regions, shell contrast and a large lower panel to remain identifiable from a distance without requiring constant giant mechanism motion.

### TRANSLATION INTERPRETATION

A phone cannot reproduce hall-distance identity, peripheral light spill, neighboring-cabinet comparison, large-area luminosity or human-scale proportions. But it gains something different: the display is physically close, occupies a large fraction of the user's focal field, and follows the player anywhere.

This is not equivalent presence.

`HALL PRESENCE` is environmental and architectural.

`PERSONAL-SCREEN PRESENCE` is close-field and attentional.

A digital translation should not be credited with cabinet presence merely because the screen is visually intense.

### REUSABLE PRINCIPLE

`SCREEN IMMERSION IS NOT CABINET PRESENCE.`

`TRANSLATION SHOULD RECORD WHICH KIND OF PRESENCE WAS REPLACED, NOT PRETEND IT WAS PRESERVED.`

## 9. Public-store evidence and its limits

### APP-SOURCED FACT

The App Store listing for the current title exposes four iPhone screenshots, confirms iPhone support, and identifies Sammy Networks as developer/distributor. The launch release confirms 2026-02-19 distribution through 777Real.

### QA LEAD — NOT FACT ABOUT IMPLEMENTATION QUALITY

App Store reviews include a complaint that this title's image quality is poor. Other reviews report crashes or simulation-behavior concerns. These are individual reports and are not sufficient to establish exact render resolution, scaling mode, frame pacing, probability behavior or device-specific defect rates.

### UNRESOLVED

This run does not claim direct controlled observation of the installed 777Real build, therefore the following remain unresolved:
- exact portrait/landscape behavior in actual play;
- exact machine viewport dimensions on current iPhone models;
- reel pixel height/width and symbol legibility threshold;
- whether machine view can be zoomed or enlarged;
- whether service UI is persistent, transient or configurable during play;
- exact LCD/reel/control cropping at different aspect ratios;
- exact lamp/side-panel animation retained from cabinet;
- exact representation of reel-window depth/material reflections;
- frame pacing and scaling quality under motion;
- haptic substitution for physical button/mechanism feedback.

## 10. Phase B visual/mechanism retained model

The strongest result of this run is not “the app looks like the cabinet.” It is a translation model:

### Real cabinet

`PHYSICAL SILHOUETTE`
+ `MATERIAL/DEPTH SEPARATION`
+ `DEDICATED REEL WORK SURFACE`
+ `TACTILE BODY MAP`
+ `ONE MACHINE VISUAL AUTHORITY`

### Smartphone app

`FLAT MACHINE CONTEXT`
+ `PIXEL ALLOCATION`
+ `TOUCH BODY MAP`
+ `ASSIST/AUTO RESPONSIBILITY`
+ `MACHINE UI + SERVICE UI`

The app can preserve the machine's state graph and recognizable composition while changing the player's visual/mechanical contract substantially.

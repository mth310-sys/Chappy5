## Integrated real-machine model

### 1. The machine carries two reward clocks

The central A+ART structure is not one continuous upper-state ladder. A real BIG is an immediate, locally valuable reward; ART is a persistent future-game resource. Their coexistence is the architectural study target.

Reusable principle:

`SHORT REWARD MAY TAKE THE FOREGROUND WITHOUT ERASING THE PERSISTENT STATE IT INTERRUPTS.`

### 2. One body map, changing responsibility

The physical lever / MAX BET / three STOP coordinates remain stable while responsibility changes by state:

- normal: routine play with intermittent rare-role aiming duty;
- ART: navigation/order compliance becomes primary when instructed;
- BONUS: reward-specific aiming/choice behavior temporarily takes foreground.

Reusable principle:

`STATE COMPLEXITY CAN LIVE ABOVE A STABLE PHYSICAL BODY MAP.`

### 3. Reel result and consequence can close at different times

STOP3 can settle the visible role while the LCD/audio layer keeps the consequence question open: bonus overlap, CZ/state movement, ART connection, extension, or return.

Reusable principle:

`STOP3 CAN CLOSE ROLE IDENTITY WHILE PRESENTATION KEEPS OUTCOME OPEN.`

### 4. State-relative value is more important than role novelty

The same visible role vocabulary is repriced by current state. A rare role is not merely an isolated event; it can be a different resource in normal, CZ, BONUS, ART, extension, or end-preparation contexts.

Reusable principles:

`THE SAME REEL EVENT CAN BECOME A DIFFERENT GAME RESOURCE IN DIFFERENT STATES.`
`ROLE IDENTITY MAY BE STABLE WHILE ROLE VALUE IS STATE-RELATIVE.`

### 5. Temporary foreground states require a return address

Across visual, audio and QA research, BIG inside ART is best modeled as:

`ART HOME → BIG FOREGROUND → BIG RESOLUTION → ART RE-ANCHOR`

The quality question is not only how strongly BIG announces itself, but how cheaply the player can recover the persistent ART context afterward.

Reusable principle:

`A PARALLEL REWARD SHOULD HAVE A CLEAR RETURN ADDRESS.`

### 6. Long-session fatigue is semantic as well as sensory

The strongest cross-director fatigue risk is not simply loudness or animation density. It is the number of simultaneously unresolved questions and the latency before the player can safely return to a trusted home routine.

Retained QA measures:

- `CONSEQUENCE CLOSURE LATENCY`
- `HOME RECOGNITION LATENCY`
- `RE-ANCHOR LATENCY`
- `CONCURRENT CLAIM COUNT`
- `RELIEF DEPENDENCE RATIO`
- `BIG-ONLY SATISFACTION`
- `BASE-ART INDEPENDENCE`

Reusable principle:

`THE MACHINE MUST LET THE PLAYER RETURN TO A TRUSTED HOME ROUTINE AFTER EACH TEMPORARY CONTEXT, OR PARALLEL DEPTH TURNS INTO PARALLEL FATIGUE.`

## Why Phase B is now useful

The Human directive is to study the real machine first, then its smartphone application, then the translation between them. Phase A now supplies a comparison frame strong enough to prevent the app from becoming retroactive evidence about the cabinet.

Phase B is therefore not a second machine study. It is a **translation study**.

The primary licensed target is the 777Real smartphone version distributed by Sammy Networks. Public store/release material confirms:

- title: `[777Real]SLOT魔法少女まどかマギカ2`;
- developer/seller: Sammy Networks Co., Ltd.;
- release: 2026-02-19;
- iPhone listing exists and requires iOS 12.0 or later;
- the App Store listing currently shows version 1.0.1 dated 2026-03-24;
- the store package listing is 142.5 MB, while user reports indicate additional in-app machine-data installation can be materially larger; package size and installed footprint must not be conflated;
- 777Real is a service layer around the machine simulation, so service economy/UI must be separated from machine translation.

A second licensed implementation also exists in グリパチ. It may be used later as a comparison control because its App Store description explicitly documents app-layer UI behavior such as top data counter, bottom menu and hide/show behavior. It must not be merged with 777Real observations.

## Phase B evidence rules

Every Phase B research file must label evidence as one of:

- `APP-SOURCED FACT` — official/store/service documentation;
- `DIRECT APP OBSERVATION` — visible behavior from actual app footage/screenshots/use;
- `REAL-MACHINE BASELINE` — already established Phase A fact, cited back to the real-machine research;
- `TRANSLATION INTERPRETATION` — reasoned comparison, never presented as implementation fact;
- `UNRESOLVED` — not safely established.

User reviews may identify QA hypotheses such as image quality, crashes, install behavior or simulation complaints, but are not authoritative evidence that machine probabilities or control differ from the real machine.

## Phase B shared questions for all five Directors

### Machine Director

Study what the app treats as the machine boundary versus 777Real service boundary. Determine whether the core repeated loop remains legible when cabinet, hall, physical credit handling and embodied operation disappear.

### Game & Reel Director

Study reel representation, stop input, timing, aimability, navigation, bonus/ART state continuity, autoplay/speed assistance where documented, and whether digital assistance changes the skill/attention economy. Do not infer undisclosed simulation/control tables.

### Visual & Mechanism Director

Study portrait-screen hierarchy, cabinet/reel/LCD cropping or scaling, control hit targets, data-counter/menu overlays, visibility modes, depth/material/LED translation, and what is omitted because a phone has no physical cabinet.

### Sound & Experience Director

Study how cabinet audio becomes phone audio: baseline cue audibility, BGM/voice/cue hierarchy, interruption/foreground/re-anchor behavior, mute/volume/service controls where documented, and the loss or substitution of hall-scale speaker/low-frequency/tactile effects. Do not reproduce protected audio.

### Playtest & QA Director

Study first-five-minute comprehension, one-handed/two-handed interaction, repeated STOP ergonomics, accidental taps, UI occlusion, battery/heat/loading/crash friction where reliably observable, auto-play effects on attention, and whether app convenience preserves or destroys the real-machine loop. Separate simulation fidelity from service friction.

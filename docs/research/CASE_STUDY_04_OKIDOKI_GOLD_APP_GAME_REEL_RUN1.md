## 2. Manual loop versus simulator loop

### REAL-MACHINE FACT — REFERENCE ONLY

Phase A established the repeated real-machine loop as:

`LOW-COST PHYSICAL HOME → LEFT REFERENCE AIM → CONDITIONAL FOLLOW DUTY → 3 STOP → WAIT / OPTIONAL INFERENCE → DIRECT TRUTH SIGNAL → BIG/REG → POST-BONUS 32G QUESTION → CHAIN OR CLOSURE`.

The ordinary procedure is low-cost but still player-driven: the player advances each game, performs the stops, and conditionally increases precision when the first stop exposes a watermelon-follow branch.

Reference:
- `CASE_STUDY_04_OKIDOKI_GOLD_GAME_REEL_RUN1.md`

### SOURCED APP FACT

The App Store listing confirms an optional `オートプレイ` add-on with selectable ending conditions and an optional `ウェイトカット` that cuts reel wait.

### INTERPRETATION

The phone version therefore supports at least two fundamentally different play contracts:

1. **manual simulator contract** — player still owns game advancement and stop actions;
2. **automation contract** — some or all repetitive advancement can be delegated to the simulator.

Wait cut changes time without necessarily changing state law. Auto play changes authorship of the repeated motor loop.

These are not equivalent conveniences.

### REUSABLE TRANSLATION PRINCIPLE

**TIME COMPRESSION AND ACTION DELEGATION MUST BE EVALUATED SEPARATELY.**

- Wait cut asks: `what survives when dead time is removed?`
- Auto asks: `what survives when the player no longer performs the repeated action?`

A simulator can preserve state outcomes while substantially changing the game experience if the repeated physical ownership disappears.

## 3. Three STOPs on touch: known responsibility and unresolved geometry

### SOURCED APP FACT

The app is an iPhone simulator of the machine. The public listing does not publish a detailed touch-control manual, STOP hitbox dimensions, frame timing, touch latency or the exact manual input grammar.

### PUBLIC APP-STORE USER REPORT

A March 27, 2024 App Store review describes paid auto operation with normal/high-speed modes and says it can be stopped at an arbitrary point. The same reviewer says high-speed mode can skip/cut BONUS consumption and reports restrictions around some forced-role use and some unusual-order play. These statements are user reports, not manufacturer documentation.

Source:
- App Store review section on the official listing above.

### INTERPRETATION

The core Game & Reel translation question is not whether three graphical STOP buttons exist. It is whether manual phone play still creates a meaningful sequence:

`SEE / ANTICIPATE → TOUCH STOP1 → READ RESULT → TOUCH STOP2 → TOUCH STOP3 → RESOLVE`.

If the touch implementation allows this sequence at readable scale and stable timing, the same logical responsibility can survive even though lever mass, button travel, finger posture and cabinet spacing are gone.

If automation bypasses it, the reels become observed output rather than authored action.

### UNRESOLVED

Without direct app execution in this run, the following remain unresolved:
- exact portrait/landscape orientation during play;
- exact reel pixel share and symbol readability;
- touch target size and whether STOP areas support multi-touch or rapid sequential taps;
- touch-to-stop latency;
- whether manual stop timing has any simulator-specific assistance;
- exact handling of invalid/alternate stop order in normal play;
- whether manual left-reference aiming is practically readable on all supported iPhone sizes.

No answer is invented from screenshots or the real-machine control model.

## 4. Setting change and forced roles create an experimental layer, not normal play

### SOURCED APP FACT

The App Store listing explicitly offers:
- `設定変更` — arbitrary setting selection at game start;
- `強制役` — forcing a small-role/BONUS flag;
- save/restart capability.

### INTERPRETATION

These tools change the simulator from only a play reproduction into a laboratory surface.

They allow questions such as:
- how repeated play feels under a fixed selected setting;
- how a known role is presented when deliberately invoked;
- how a BONUS transition or direct notification can be revisited without waiting for natural occurrence;
- how a post-BONUS sequence can be inspected repeatedly.

But they also destroy natural frequency and anticipation if left on during experiential evaluation.

### REUSABLE TRANSLATION PRINCIPLE

**SIMULATOR DEBUG POWER SHOULD BE USED TO ISOLATE STATES, THEN DISABLED WHEN JUDGING THE NATURAL LOOP.**

`STATE ACCESS TEST ≠ NATURAL EXPERIENCE TEST`.

A forced role is useful evidence for presentation/state access, not evidence of how often the player would encounter that event or how suspense accumulates naturally.

## 5. Public reports show the simulator intentionally withholds some hidden-state visibility

### PUBLIC APP-STORE USER REPORT

Several App Store reviewers ask for capabilities such as current-mode display, specific definite-role selection, cherry A/B probability display or more direct control over hidden state. A March 27, 2024 review reports that mode display/selection and some role forcing are not available; a May 6, 2024 review similarly requests current-mode display and more detailed forced-role/probability functions. A February 2, 2025 review reports restrictions on forced roles inside 32G.

These are user reports and may describe particular app versions or misunderstandings. They are not promoted to `SOURCED APP FACT` unless the manufacturer documents them.

Source:
- review section of the official App Store listing.

### INTERPRETATION

This is an important boundary for research quality: a licensed simulator does not necessarily expose the machine as a transparent state debugger.

The app can reproduce play while still preserving opacity around hidden mode law.

### REUSABLE TRANSLATION PRINCIPLE

**A SIMULATOR CAN REPRODUCE PLAYER-FACING BEHAVIOR WITHOUT BECOMING AN INTERNAL-STATE INSPECTOR.**

Do not mistake lack of a mode display for lack of a mode, and do not infer a hidden transition table from repeated simulator outcomes.

## 6. The 32G horizon under manual play

### REAL-MACHINE FACT — REFERENCE ONLY

Phase A found that post-BONUS value is strongly organized around a 32G resolution horizon. This short horizon is part of why the same physical HOME can feel radically different after a BONUS.

### SOURCED APP FACT

The official app reproduces the machine and offers manual play in its base simulator, while wait-cut and auto are optional paid functions rather than the only mode of play.

### INTERPRETATION

In manual phone play, the 32G horizon can remain structurally meaningful if the player must still advance and stop each game. The number of remaining games becomes a compact countdown of owned actions:

`32 → repeated manual games → next direct answer / closure`.

Even without cabinet mass, the sequence can preserve prediction because the player still pays the action cost for each unresolved game.

### REUSABLE TRANSLATION PRINCIPLE

**A RESOLUTION HORIZON IS FELT THROUGH BOTH GAME COUNT AND ACTION COST.**

Two interfaces may both contain exactly 32 logical games but produce different tension if one requires 32 owned interactions and the other consumes them automatically.

---

## 7. The 32G horizon under wait cut

### SOURCED APP FACT

Wait cut is explicitly offered as an add-on that cuts reel wait.

### INTERPRETATION

Wait cut compresses elapsed time while preserving, in principle, the count of games and manual STOP opportunities. This can strengthen iteration and research convenience without necessarily deleting the 32 decision/action units.

However it can also change cadence:

`BET/START → reel movement → STOP → settle → next game`

becomes denser, leaving less perceptual release between cycles.

### REUSABLE TRANSLATION PRINCIPLE

**ACCELERATION PRESERVES GAME COUNT BUT CHANGES ATTENTION DENSITY.**

For app QA, `32 games completed` is not enough. Measure whether the player can still perceive individual game boundaries and notification timing when wait is removed.

---

## 8. The 32G horizon under auto/high-speed play

### SOURCED APP FACT

Auto play with selectable ending conditions is an official optional function.

### PUBLIC APP-STORE USER REPORT

The March 27, 2024 review distinguishes normal and high-speed auto and reports that high-speed operation can cut BONUS consumption. This is not official documentation of exact speed or behavior.

### INTERPRETATION

Auto can turn the 32G horizon from a sequence the player performs into a condition the player monitors.

Manual:
`I AM DOING THE NEXT 32G.`

Auto:
`THE APP IS SEARCHING THE NEXT 32G FOR ME.`

This is a meaningful change in prediction ownership. The direct lamp/notification can remain exciting, but the tension may shift from embodied anticipation to result surveillance.

High-speed operation may intensify this shift further: if intermediate reel cycles become too fast to read individually, the reels cease to be repeated evidence and become transition animation between state checks.

### REUSABLE TRANSLATION PRINCIPLE

**AUTOMATION CAN PRESERVE OUTCOME UNCERTAINTY WHILE REMOVING ACTION UNCERTAINTY.**

The player may still not know whether a BONUS will arrive, but they no longer decide or perform each step toward the answer.

## 9. Player skill and payout relationship on phone

### REAL-MACHINE FACT — REFERENCE ONLY

Phase A found low but non-zero reel responsibility: ordinary left-reference aiming and conditional watermelon follow protect handling accuracy, while BONUS stop-order knowledge can increase information yield. This is not 新ハナビ-style high-frequency technical intervention.

### INTERPRETATION

The smartphone translation potentially separates three kinds of skill:

1. `MOTOR AIMING SKILL` — visually identify and touch at useful reel timing;
2. `PROCEDURAL KNOWLEDGE` — know when follow duty or order responsibility changes;
3. `STATE/ROLE INTERPRETATION` — understand what observed forms imply.

Touch play may reduce physical-button difficulty without removing procedural knowledge. Auto may remove both motor execution and much of procedural burden while leaving only outcome/state interpretation.

This suggests a useful comparison matrix for later Playtest/QA:

| Mode | Motor ownership | Procedural responsibility | Outcome uncertainty |
|---|---|---|---|
| Manual / normal wait | high relative to app | high | preserved |
| Manual / wait cut | high relative to app | high | preserved; cadence compressed |
| Auto normal | delegated | reduced | preserved |
| Auto high-speed | strongly delegated | strongly reduced | preserved but sampled more like surveillance |
| Forced-role test | player-triggered laboratory action | artificial | intentionally reduced/removed for target event |

This table is an interpretation framework, not a claim about exact app control internals.

### REUSABLE TRANSLATION PRINCIPLE

**CONVENIENCE OPTIONS SHOULD BE TREATED AS DISTINCT PLAY MODES WHEN THEY CHANGE WHO OWNS THE REPEATED ACTION.**

## 10. 100G / 500G / extended-session implications

### 100G — manual

**INTERPRETATION**

A manual 100G app session can still test the repeated reel contract: whether left-reference aiming is readable, whether conditional follow interrupts routine at the right frequency, whether touch STOP remains satisfying, and whether notification anticipation survives without cabinet hardware.

This is the closest app condition to judging preservation of the real-machine repeated loop, though it must still be treated as a phone experience rather than a substitute for cabinet play.

### 100G — automated

**INTERPRETATION**

Auto 100G tests something else: the value of state monitoring after repeated action has been delegated. If the experience remains compelling, that demonstrates strength of notification/horizon structure, not preservation of the three-STOP game loop.

### 500G dry interval

**INTERPRETATION**

On manual play, a dry 500G interval exposes touch repetition, screen vigilance and attention fatigue. On auto/high-speed, it exposes whether convenience converts an intrinsically thin interval into mere waiting for a state change.

A simulator that makes 500 dry games painless through acceleration has improved access, but that does **not** prove the underlying 500-game loop has become engaging.

### Extended / ~3 hour phone use

**UNRESOLVED / TEST REQUIREMENT**

Direct app execution is required before making claims about thumb/finger fatigue, screen heat, battery, posture, touch precision degradation or visual fatigue. The App Store listing itself warns about device/support conditions but does not establish long-session ergonomics.

### REUSABLE TRANSLATION PRINCIPLE

**ACCELERATION CAN REMOVE EXPOSURE TO A WEAK LOOP; IT MUST NOT BE CREDITED AS EVIDENCE THAT THE LOOP SURVIVED TRANSLATION.**

## 11. What this app can and cannot teach Game & Reel

### CAN TEACH / SUPPORT

- how a licensed simulator exposes manual versus delegated repetition;
- how optional wait removal changes cadence;
- how setting selection and forced roles can isolate state presentation for research;
- whether a short post-BONUS horizon remains meaningful when the cabinet is removed;
- how much of the game remains when physical effort is reduced;
- where convenience crosses from access aid into a different play contract.

### CANNOT PROVE

- undisclosed real-machine stop-control tables;
- exact hidden mode transition law;
- exact real-machine role probability when the app itself warns simulation values may differ;
- exact physical reel timing, button travel or cabinet input feel;
- that a state exposed with a forced-role tool has natural frequency or natural emotional buildup;
- any protected internal implementation.

## 12. Game & Reel app-study verdict

The official iPhone app exposes a valuable separation that is harder to see on the cabinet:

**THE STATE MACHINE, THE REEL-ACTION LOOP, AND THE ELAPSED-TIME COST CAN BE MODIFIED INDEPENDENTLY.**

The base/manual simulator appears intended to preserve player-facing machine play, while paid wait-cut and auto tools deliberately let the user remove time cost and/or repeated action ownership. Setting and forced-role options add a laboratory layer on top.

For Chappy5 research, the key reusable conclusion is not “apps should have fast-forward.” It is:

**WHEN TRANSLATING A PACHISLOT LOOP TO PHONE, IDENTIFY WHICH PART OF TENSION COMES FROM UNKNOWN OUTCOME, WHICH COMES FROM THE NUMBER OF ACTIONS UNTIL RESOLUTION, AND WHICH COMES FROM THE PLAYER PERSONALLY PERFORMING THOSE ACTIONS.**

The 32G horizon is therefore a particularly useful test object. It can remain 32 logical games while feeling materially different across manual, wait-cut and auto modes.

No claim is made here that the app perfectly preserves physical reel readability or touch-stop feel because direct app execution was not available in this run.

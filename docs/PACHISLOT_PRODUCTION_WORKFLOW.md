> Status: `DRAFT_BEFORE_INDUSTRY_RESEARCH`
>
> この文書は、実際のパチスロメーカー／遊技機開発会社の制作工程を本格調査する前に作る**下地**である。
> 現時点の工程名・順序・担当区分を「実際の業界工程」として確定してはならない。

## 1. この文書の役割

READMEはChappy5全体の憲法とし、この文書は**「パチスロ1機種をどのような制作工程で完成させるか」**を管理する制作工程正本候補とする。

正式化後は、READMEには最上位原則と固定5 Director体制を残し、制作工程の詳細は本書を参照する構造を目指す。

文書階層：

1. `README.md` — Chappy5全体の最上位原則・固定体制・禁止事項
2. `docs/PACHISLOT_PRODUCTION_WORKFLOW.md` — パチスロ制作工程
3. 各機種SPEC — その機種で何を作るか
4. テスト・検証記録 — 実際に何が確認されたか

---

## 2. 最終目標

Webゲーム一般の開発手順ではなく、**実際のパチスロ機開発の考え方・分業・並行制作・統合・試打・調整に可能な限り近い制作工程**をChappy5上へ構築する。

ただし、物理製造・法規申請等、Chappy5のブラウザパチスロ制作に存在しない工程を無理に模倣することを目的としない。

調査後は、実業界工程を以下に分類する。

- Chappy5でもそのまま再現すべき工程
- デジタル環境向けに置換して再現すべき工程
- 参考思想だけ採用すべき工程
- Chappy5では不要な工程

---

## 3. 固定5 Directorとの関係

制作開始から完成まで役割は固定する。

- Machine Director — 機種全体・商品性・統合判断
- Game & Reel Director — ゲーム性・数理・リール・制御
- Visual & Mechanism Director — 映像・筐体・役物・機構
- Sound & Experience Director — SE・BGM・告知・音響演出
- Playtest & QA Director — 目＋手＋耳による実遊技・品質検証

**工程に合わせてDirectorを入れ替えない。**

実際の業界調査でより細かな職種が見つかった場合も、Chappy5では原則としてこの5 Directorのどこへ責務を割り当てるかを定義する。

## 4. 調査前の仮工程マップ

以下は正式工程ではない。調査時に検証・修正するための骨組みである。

### Stage A — 企画・商品構想

仮対象：

- 市場・競合研究
- ターゲット
- 機種コンセプト
- 世界観・モチーフ
- コアとなる遊技体験
- スペック骨格
- リールの特徴
- 筐体／役物コンセプト
- Visual Concept
- Audio Concept
- 「この台を打つ理由」の定義

成果物候補：企画書／コンセプト資料。

Human Gate候補：機種採択。

### Stage B — 基本仕様・ゲーム設計

仮対象：

- ゲームフロー
- 通常時
- 内部状態
- 当選契機
- BONUS / CZ / AT / 上位状態
- 出玉設計
- 設定差
- リール配列
- 役構成
- 停止・出目・押し順／目押し要素
- 演出期待度構造
- 遊技テンポ

成果物候補：基本仕様書／ゲームフロー／数理仕様／リール仕様。

### Stage C — 筐体・役物・Visual設計

仮対象：

- 筐体外観
- 液晶領域
- リール領域
- 操作部
- LED
- 可動役物
- 新機構
- 画面レイアウト
- 図柄
- UI
- 演出階層
- 過去遊創舎資産の再利用・改造・融合

成果物候補：筐体設計／Visual Design／Mechanism Design。

### Stage D — 演出・映像・Audio制作

仮対象：

- 通常演出
- 前兆
- チャンスアップ
- 当落
- 告知
- BONUS / AT演出
- 上位演出
- SE
- BGM
- ジングル
- 状態別音響
- Visual・役物・Audio同期

成果物候補：演出仕様／演出素材／Audio仕様・素材。

### Stage E — 制御・組込み

仮対象：

- 抽選実装
- 状態遷移
- リール制御
- BET / START / STOP
- 演出制御
- LED／役物制御
- Audio Event
- UI
- persistence
- 将来のhost bridge

ここでは「プログラムを作ること」自体を完成条件にしない。

### Stage F — 統合機・実遊技化

仮対象：

- Game + Reel + Visual + Mechanism + Audioの統合
- 通常→当たり→主要状態→終了→復帰の接続
- Unified Playtest
- 実ブラウザでの連続遊技

成果物候補：統合ビルド／統合検証記録。

### Stage G — デバッグ・数理検証

仮対象：

- 状態到達性
- 抽選責務
- リール整合
- 100G / 1,000G / 10,000G等の試行
- 偏り
- 破綻
- 無限ループ
- 復帰
- 入出力
- Audio/Visual同期

数理試行と実遊技試打を混同しない。

### Stage H — 試打・評価・調整

仮対象：

- 通常時は本当に回したいか
- 当たりを期待できるか
- 出目が気持ちいいか
- 演出期待度が理解できるか
- 告知が気持ちいいか
- BONUS/ATに価値を感じるか
- Visual・Mechanism・Audioが一体化しているか
- 長時間で退屈／過剰にならないか
- iPhone実遊技で操作しやすいか

基本ループ：

**試打 → 問題記録 → Machine Director統合判断 → 担当修正 → 再統合 → 再試打**

### Stage I — 最終品質・完成判定

仮対象：

- 主要ルート完成
- 既知重大不具合
- 数理整合
- Visual確認
- Audio確認
- Unified Playtest
- 長時間試打
- Human評価

Human Gate候補：`HUMAN_MACHINE_VERIFIED`。

## 5. 並行制作の考え方

正式調査で特に確認する。

現時点では、基本仕様が成立した後、以下が**完全直列ではなく並行して進み、統合地点で合流する**構造を仮説とする。

- Game / Spec / Reel / Control
- Cabinet / Mechanism
- Visual / Effect
- Sound / Audio

ただし各ラインが独立作品のように暴走してはならない。Machine Directorが同じ機種コンセプト・仕様を基準に統合する。

## 7. 本格調査で確認する事項

調査では少なくとも以下を確認する。

1. 実際のパチスロメーカーで企画がどのように始まるか。
2. 企画、出玉設計、リール／制御、映像、サウンド、筐体／役物、プログラム、品質保証の職種・責任分担。
3. どの工程が直列で、どの工程が並行するか。
4. 仕様書・企画書・演出仕様等、工程間で何を受け渡すか。
5. 試作機／開発機／評価機に相当する段階が存在するか、どのように使われるか。
6. リール配列・停止制御・出玉設計がいつ固まるか。
7. 映像演出とゲーム仕様がどの時点で結合するか。
8. サウンド制作がいつ入り、何と同期して制作されるか。
9. 筐体・役物の企画から組込みまでの流れ。
10. デバッグ・数理検証・試打・調整の反復方法。
11. 商品性／面白さの評価がどの段階で行われるか。
12. 実際の製造・型式試験・法規対応等のうち、Chappy5に思想として取り込む価値がある部分。
13. ブラウザ上のChappy5では何へ置換すべきか。

## 8. 情報源の優先順位

正式調査では、可能な限り以下の順で重視する。

1. パチスロ／遊技機メーカー公式の採用・職種・開発紹介
2. 遊技機開発会社・協力会社の公式な開発工程／職種説明
3. 業界団体・技術資料・公的資料
4. 開発者インタビュー
5. 信頼性を確認できる専門媒体
6. その他二次情報

一つの会社の工程を「業界全体の唯一の正解」としない。複数社を比較し、共通部分と会社固有部分を区別する。

## 9. 調査後の正式化手順

1. 実業界の制作工程を資料ごとに抽出する。
2. 複数社の共通工程と相違点を比較する。
3. 現在のStage A〜I仮説と照合する。
4. 間違っている工程名・順序・責任範囲を修正する。
5. Chappy5に存在しない物理工程／法規工程を分類する。
6. 必要な思想・Gate・検証をデジタル工程へ置換する。
7. 固定5 Directorへ各職能を割り当てる。
8. 各工程のInput / Output / Exit Criteriaを確定する。
9. Human Gate位置を確定する。
10. Statusを `DRAFT_BEFORE_INDUSTRY_RESEARCH` から正式状態へ変更する。
11. READMEから本書を正式参照する。

```text

= categoryBaseOut
× popularityFactor
× ageFactor

```

## 3. Day 1個体差の狙い

同じアイムジャグラーEXでも、S001とS018を同じ稼働にはしない。

例:
- S001: アイムジャグラーEX / 設定4 / 主力現役 / 人気高
- S018: アイムジャグラーEX / 設定1 / 主力現役 / 人気高

開店直後は設定を客が知らないため、朝の着席力は大差を付けない。営業中にボーナス履歴が形成されることで、S001の高設定が観測されれば後半の粘り・再着席へ効く。

逆に設定5でも短期的に結果が悪ければ、その日の客には高設定と認識されない可能性を残す。

## 7. 個体レベルで起こすイベント

営業中に各台について以下を生成する。

- 着席/離席
- OUT増加
- BIG/REG/RT/ART当選
- 実績セーフ
- 客側差枚
- データ表示器履歴
- 空席時間
- 再着席

個体の出玉結果はカテゴリ平均へ強制的に戻さない。

そのため同じ島に、
- +2,000枚級
- ほぼトントン
- -2,000枚級
- 低稼働で判別不能

が同時に存在する。

## 8. 客AIへのDay 1観測

客AIへ渡すのは真の設定ではなく観測値。

例:

```text
observedMachineStrength_i
= visibleBonusPerformance
+ visibleDifference
+ persistenceSignal
+ neighboringMachineSignal
```

Day 1終了時に、

- 25Φ: やや弱い
- 30Φ: 弱め
- A+RT: 今日だけ見ると強く見える
- ART/CZ: 新しいが回収感あり
- 旧台: 稼働そのものが弱く判別材料不足

という印象が形成される想定。

これは真の設定配分と必ずしも一致しない。短期結果を客が誤認することもゲーム性として保持する。

## 9. 翌日への状態更新

Day 1終了後、各instanceへ保存する。

```text
previousDayOut = actualOut
previousDayDifference = customerDifference
previousDayVisibleHistory = {...}
machineExpectation = updatedValue
```

さらにカテゴリ/島/店舗へ集約する。

```text
categoryExpectation
islandExpectation
hallExpectation
```

これをDay 2の来店・台選択・粘りへ接続する。

## 10. ゲーム本体への接続点

このDay 1モデルは最終的に以下へ直接つなぐ。

```text
MachineMaster(real DB-derived fictional spec)
        ↓
MachineInstance(S001-S130)
        ↓
Customer AI
        ↓
13h Sales Simulation
        ↓
OUT / SAFE / 差枚 / 売上 / 粗利
        ↓
Data Counter / Management UI
        ↓
Customer Memory
        ↓
Day 2
```

つまり研究DB・130台台帳・経営計算は別々の資料で終わらせず、同じゲームループの入力/状態/出力として接続する。

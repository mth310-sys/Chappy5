設定は既存台帳のまま。

```text
expectedSafe_i = actualOut_i × payoutRate_i(setting_i)
expectedGross_i = (actualOut_i - expectedSafe_i) × 20円
```

を計算して合計。

## 5. 重要な意味

同じ「A+RTに設定を入れる」でも機種によってコストが違う。

- スパイダーマン2: 設定2 99.8%、設定3 102.8%、設定4 107.3%
- リングにかけろ1: 設定2から100.5%、設定3 103.0%
- 初代エヴァ: v0.1採用系列では設定2 98.0%、設定3 100.6%
- ツインエンジェル: v0.1採用系列では設定2 99.2%

そのため、プレイヤーは「高設定を何台」だけでなく、**どの機種へどの設定を使うか**で営業コストを変えられる。

## 6. まだ仮定の部分

今回、実機DBから確定的に使っているのは設定別機械割。

以下はまだゲーム側の仮定:

- Day 2 A+RT OUT +8% / +15%
- 32台へのOUT分散重み
- Strategy Bで変更する8台
- 日次確率ブレ
- 客の技術介入

したがって本結果は「実機DBを使った経済エンジンが動くか」の検証値。

## 7. 次段階

次はOUTターゲット自体を外す。

```text
customer arrival
→ machineMemory/categoryMemory
→ seatScore
→ 着席
→ 1時間ごとの継続/離席
→ actualOut
→ 実機DB payout
→ SAFE/粗利
```

の順にS059〜S090を動かす。

これにより「Strategy Bだから+15%」ではなく、設定投入の結果が客に観測され、実際に着席が増えた結果としてOUTが伸びる方式へ移行する。

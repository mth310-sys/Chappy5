# 開始ホール Day 1 13時間営業シミュレーション v0.1

更新日: 2026-09-01

目的: `START_HALL_DAY1_INSTANCE_SIMULATION_V01.md` の日次結果を10:00〜23:00へ分解し、S001〜S130が営業画面上で時間とともに変化する計算構造へ接続する。

**位置づけ:** ゲーム本体接続用の構造検証値。正式バランスではない。

## 1. 営業時間

- 開店: 10:00
- 閉店: 23:00
- 営業時間: 13時間
- ゲーム上の1営業日: 実時間約3〜5分を目標
- プレイヤー操作: 一時停止 / 標準 / 高速を想定

営業フェーズ中は設定変更・台移動などの大きな経営操作を行わず、プレイヤーは店内の状況を観察する。

## 3. 時間帯の客行動

### 10:00〜12:00

- 常連・朝から打てる客が中心
- 前日履歴や機種好みを重視して着席
- Day 1では店の設定情報が少ないため、真の高設定台と低設定台の朝稼働差は小さい
- 人気ノーマル、30Φ、話題機が先に埋まる

### 12:00〜17:00

- 朝客の結果がデータ表示器へ蓄積
- ボーナス回数、差枚、周辺台の出玉が設定推測材料になる
- 弱い台から離席が増え、良さそうに見える台へ再着席が起きる
- バラエティの低人気台は空席時間が長くなる

### 17:00〜21:00

- 仕事帰り流入で店全体のピーク
- 空き台の履歴を見て台を選ぶ客が増える
- A+RT島がDay 1で客側プラスに見えているため再着席率が上がる
- ノーマル/沖スロはボーナス履歴から粘る客と見切る客が分かれる

### 21:00〜23:00

- 残り時間が台選択に影響
- ノーマルは短時間勝負として一定需要を維持
- 長いRT/ARTを期待する機種は新規着席が低下
- 既に持ちメダル/ART状態の客は継続するため全台一律には落ちない
- 22時以降は閉店取り切れずリスクを客AIが考慮する

## 4. 1時間ごとの machineInstance 更新

各S001〜S130について1時間ブロック内で以下を更新する。

```text
occupied
currentCustomerId
hourOut
cumulativeOut
bonusCount
rtArtState
safe
customerDifference
visibleHistory
customerInterestScore
```

1時間の開始時に全結果を決め打ちするのではなく、内部では数十秒〜数分相当の小tickに分けられる構造にする。

## 5. 着席判定

客が空き台を選ぶ際の候補スコア:

```text
seatScore
= machinePreference
+ machinePopularity
+ visibleHistoryScore
+ categoryExpectation
+ islandExpectation
+ hallExpectation
- closingRisk
```

設定値そのものはseatScoreへ入れない。

Day 1朝は `visibleHistoryScore` が弱く、時間経過とともに重みが増える。

## 6. 離席判定

着席中の客は一定間隔で継続判断する。

候補要因:

- 所持金/持ちメダル
- 滞在可能時間
- 現在差枚
- ボーナス/小役等からの設定推測
- 隣接台/島の出玉
- 客タイプの粘り強さ
- 閉店までの残り時間

したがって同じ設定1でも、偶然好調な台は長く回されることがあり、設定4でも悪い展開なら早く捨てられる。

## 7. OUT生成を客行動へ接続

従来の日次モデルの `actualOut` を直接生成する方式から、13時間モデルでは:

```text
着席時間
× 遊技速度
× リプレイ/ボーナス/RT/ART状態
→ hourOut
```

として積み上げる。

日次OUTは:

```text
actualOut_i = Σ(hourOut_i[10..22])
```

ホール全体は:

```text
totalOut = Σ(actualOut_i[S001..S130])
```

となる。

これにより日次572,400を先に各台へ配る必要がなくなる。

## 8. 出玉と履歴のリアルタイム反映

ボーナス等が発生した瞬間に以下を更新する。

- 台上の簡易ランプ/演出状態
- データ表示器
- 差枚推移
- 周囲の客が得る neighboringMachineSignal
- 島の「出ている感」

プレイヤーは管理画面を開かなくても、店内を眺めてある程度状態を感じられることを目標とする。

## 9. Day 1で起こす代表シーン

構造検証用に以下が同一営業日に共存できる状態を作る。

- 設定5のアイム系が午前中不発で空く
- 設定1のアイム系が偶然BIG先行し夕方まで高設定に見える
- A+RTの設定4が午後から伸び、島全体の注目を上げる
- 最新ART設定1が一撃で目立つ出玉を作り、後続客が座る
- 古いバラエティは終日0〜数人しか触らない
- 22時以降、ART/CZの空き台が増える一方、告知ノーマルには短時間客が残る

これらは演出用の固定イベントではなく、確率計算と客判断から発生可能な現象として扱う。

## 10. ゲーム画面へ渡す状態

営業画面の描画側は全計算を行わず、シミュレーション側から軽量snapshotを受け取る。

```text
HallSnapshot
- gameTime
- occupiedCount
- totalOut
- totalSales
- estimatedGrossProfit
- machineSnapshots[130]
```

各machineSnapshotは表示に必要な最小情報だけ持つ。

```text
instanceId
occupied
visibleMachineState
visibleBonusCount
visibleDifferenceBand
attentionLevel
```

詳細な設定・乱数・客記憶は描画オブジェクトに持たせない。

これはiPhone Safariで130〜216台へ拡張する際の負荷分離にも使う。

## 11. 営業速度

13時間を実時間3〜5分に圧縮する場合、標準速度ではゲーム内1時間が約14〜23秒に相当する。

内部シミュレーションtickと描画fpsは分離する。

例:

- simulation tick: ゲーム内1〜5分単位
- rendering: requestAnimationFrame
- UI集計更新: 0.25〜1秒程度

全130台の重い再計算を毎frame実行しない。

## 13. 次段階

次はDay 1の観測結果を使い、Day 2開始時に客AIがどの台・島を狙うかを変化させる。

比較する最小ケース:

1. Day 1で目立ったA+RT島へ翌朝客が増える
2. 実は高設定だったが不発だった台は評価されない
3. 低設定の誤爆台へ翌日客が集まることがある
4. 弱かったART/CZ群は新台人気だけでは稼働を維持できない
5. 店全体の信用が低いため、1日の好結果だけでは急激に満席化しない

このDay 1→Day 2接続を作ることで、ゲームの中心である `設定営業 → 結果を観察 → 客が学習 → 翌日の稼働が変わる` ループを成立させる。

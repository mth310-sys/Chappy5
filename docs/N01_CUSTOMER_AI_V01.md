# N-01 10台島 簡易客AI v0.1（暫定設計）

更新日: 2026-08-31

目的: N-01 10台島の設定配分検証を、固定アウト比較から「客が見える情報を基に判断し、その結果としてアウトが生まれる」モデルへ進める。

注意: この文書は検証用の暫定設計。客AIの最終仕様、重み、閾値、客層構成は未採用。

## 1. 基本原則

客AIは内部設定を参照しない。

客が参照できるのは原則としてホール内で観測可能な情報だけとする。

主な観測値:
- 現在ゲーム数
- BB回数
- RB回数
- BB/RB合算
- 現在差枚
- 総ゲーム数
- 周辺台のBB/RB・差枚
- 島全体の稼働
- 当日の店内の出玉感
- 過去営業から形成した店舗期待

内部設定1〜6は店長側・シミュレーション側の非公開値。

## 2. 最小行動状態

簡易客AI v0.1は次の状態を持つ。

1. ARRIVING — 入店
2. SCANNING — 空き台・島データ確認
3. PLAYING — 着席・遊技
4. REEVALUATING — 一定ゲームごとに続行判断
5. MOVING — より良く見える空き台へ移動
6. LEAVING — 退店

最終ゲームでは接客、飲食、休憩、友人連れ等を追加可能だが、設定配分検証では上記だけでよい。

## 3. 台評価の考え方

台の評価値を単一の確定設定推定値にはしない。

客は「高設定らしさ」を不確実なスコアとして持つ。

概念例:

`machine_expectation = evidence_strength × observed_performance + store_prior + island_context + personal_bias`

ここで重みは未確定。

### evidence_strength
観測ゲーム数が少ないほど低くする。

例:
- 0〜500G: 非常に弱い証拠
- 500〜1500G: 弱い
- 1500〜3000G: 中程度
- 3000G以上: 強くなる

重要: 300GでREG2回だから設定6確信、のような極端な判断を全員が行わないようにする。

## 4. N-01で使う観測指標

N-01はBBよりRBの設定差を大きめに持つ暫定設計なので、設定推測型の客はRBを強めに評価できる。

ただし全客が同じ知識を持つ設計にはしない。

最低限の観測特徴量候補:

- BB確率実績
- RB確率実績
- 合算実績
- 差枚
- 総ゲーム数
- 島内の好挙動台数
- 周辺台の稼働率
- 前日までの店舗期待

### 重要
差枚だけで設定判別させない。

低設定の誤爆、高設定の不発を残すため、BB/RB内容と試行ゲーム数を同時に見る。

## 5. 続行判断

一定ゲーム数ごと、またはボーナス後などに再評価する。

簡易構造:

`continue_score = machine_expectation + sunk_session_evidence + store_expectation - fatigue - loss_pressure`

- machine_expectation: 今の台への期待
- sunk_session_evidence: 自分が回して得た追加データ
- store_expectation: この店ならまだ上があるかもしれないという期待
- fatigue: 滞在時間による終了圧力
- loss_pressure: 投資・負け額による終了圧力

閾値を超えれば続行。
下回れば移動候補を確認し、魅力的な空き台がなければ退店。

## 6. 台移動

客AIは常に最高スコア台へ瞬間移動するような最適化AIにはしない。

候補台が現在台より十分よく見える場合のみ移動する。

これにより:
- 少し良いだけなら現在台を継続
- 明らかにREGが良い空き台なら移動
- 島全体が弱ければ退店

という人間らしい挙動を作る。

## 7. 島全体の評価

1台の設定6だけで全10台を高評価にはしない。

一方で、明確な好挙動台が複数見つかると「この島は設定を使っている」という島期待を上げる。

候補となる観測:
- 高ゲーム数かつ好合算の台数
- 高ゲーム数かつRBが良い台数
- 客側プラス台数
- 高稼働台数
- 空き台が少ない状態の継続時間

ここでも内部設定数は参照しない。

## 8. 店舗期待（翌日への持ち越し）

営業終了後、各客は当日の観測から店舗への期待を更新する。

概念:

`next_store_prior = old_prior × memory + today_observation × learning_rate`

これにより:
- 低設定中心を連日続ける → 少しずつ期待低下
- メリハリで強い台が何度も確認される → 設定狙い客の期待上昇
- 高設定を入れたが不発 → 1日だけでは評価が上がらない場合もある
- 一度強かっただけでは永久に信用されない

という状態を作る。

## 9. 最初の検証客は1種類だけにする

v0.1では客層を増やさない。

まず「ノーマル機の設定をある程度意識する常連型」の検証エージェントだけを作り、設定配分A〜Dに対して期待どおり異なる行動が出るか確認する。

この段階で確認すること:
- 低設定中心Aで翌日期待が下がるか
- 中間中心Bで極端な退店が減るか
- メリハリCで強い台発見後に島内回遊が増えるか
- 全台系Dで時間経過とともに島稼働が上がるか

これが成立してから、初心者、沖スロ固定客、短時間客、勝敗重視客などを追加する。

## 10. 営業時間の離散化

ゲーム本編は10:00〜23:00を3〜5分へ圧縮する予定だが、経営計算まで毎フレーム行う必要はない。

内部シミュレーションは営業日を複数の時間ブロックへ分ける。

候補:
- 30分単位 = 26ブロック
- 1時間単位 = 13ブロック

v0.1では1時間13ブロックで十分。

各ブロックで:
1. 新規来店判定
2. 台選択
3. 遊技結果更新
4. 台データ公開値更新
5. 続行/移動/退店判定
6. 島評価更新

を行う。

表示側は滑らかに客を歩かせても、経営ロジックはこの離散更新でよい。

## 11. 重要な実装分離

### Machine truth
- 内部設定
- 真のBB/RB確率
- 理論出玉率
- 当日の抽選結果

### Machine public state
- 総ゲーム
- BB
- RB
- 合算
- 差枚
- 現在ゲーム数

### Customer belief
- 各台への期待
- 島への期待
- 店への期待
- 確信度

この3層を分離する。

特に `Customer belief` に内部設定番号を直接渡さないことをルール化する。

## 12. 成功条件

簡易客AI v0.1は「人間を完全再現する」ことが目的ではない。

最初の成功条件は次の4点。

1. 同じ設定配分でも出玉結果によって稼働が変わる。
2. 設定6が不発なら客が必ず見抜くわけではない。
3. 設定1が誤爆すると一時的に期待されることがある。
4. 配分A〜Dが直接パラメータではなく、公開データを介して異なる稼働曲線を生む。

## 13. 次の作業

次はこの設計を使って、コード実装前の簡易数値モデルを作る。

10台島 × 13時間ブロックについて:
- 客来店数
- 着席台
- 台移動
- 退店
- 各台アウト
- 島アウト
- 売上
- 粗利
- 終日店舗期待

を記録する。

最初は客1種類のみ。
重み・閾値は採用値にせず、A〜Dの営業差が自然に発生する範囲を探索するための検証パラメータとして扱う。

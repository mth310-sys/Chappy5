# スロットパチ朗 箱庭基盤仕様書 v1

## 0. この仕様書の目的

本書は『スロットパチ朗』のうち、次の3領域だけを先に固定するための実装契約である。

1. マップ基盤
2. 施設基盤
3. 導線基盤

客AI、遊技判断、設定配分、経営計算、イベント、広告、研究、客層差分などのゲーム性は本書の対象外とする。そこから先は遊創舎独自仕様として別設計する。

本書でいう「カイロ系」は、カイロソフト作品の著作物・内部コード・固有UI・固有アセットを複製する意味ではない。公式に確認できる経営SLGの設計原則、すなわち「配置が経営結果に影響する」「施設がマップ上の実体として存在する」「客が施設へ移動して利用する」「相性や隣接が価値を生む」といった構造を、高レベルの設計原則として独自実装へ落とす。

### 参考とした公式公開情報

- ゲームショップ物語: https://kairosoft.net/game/mobile/gameshop.html
  - 棚・設備の設置場所と取扱商品によって人気・来客数が変わる。
- 開店デパート日記: https://kairosoft.net/game/appli/depart.html
  - 店舗の隣接、階段・エスカレーター等を通じた目的地への移動が重要。
- 開店デパート日記2: https://kairosoft.net/game/appli/depart2.html
  - 相性の良い店舗配置で専門フロアが成立し、配置自体が価値を持つ。
- 開店コンビニ日記: https://kairosoft.net/game/appli/convenience.html
  - 棚を自由配置し、来店客が店内を利用する構造。
- 青空 発掘カンパニー: https://kairosoft.net/game/appli/hakkutu.html
  - 売場・レジ・サービスカウンターが施設として分かれ、客の利用結果に影響する。

上記から確認できるのは設計原則までであり、グリッド寸法、経路探索アルゴリズム、内部データ構造などは公開情報ではない。本作ではそこを独自仕様として定義する。

# 1. マップ基盤

## 1.1 論理座標を唯一の正とする

全施設の配置位置は整数グリッド `(x, y)` だけで保持する。

禁止事項:

- CSS の `left/top` をゲーム状態として保存する。
- 施設ごとに独自の画面座標を持つ。
- 0.5マス等の半端な論理座標を使う。
- 見た目を合わせるためだけに施設の論理位置をピクセル単位で補正する。

画面座標は必ず論理座標から算出する。

```text
screenX = originX + (x - y) * halfW
screenY = originY + (x + y) * halfH - rise
```

現行基準:

- tileW = 26 px
- tileH = 13 px
- halfW = 13 px
- halfH = 6.5 px

`rise` は見た目上の高さだけに使い、論理セル位置には影響させない。

## 1.2 1セルの意味

1セルは「最小の建築・通行判定単位」とする。

セルは機種1台の実寸そのものではなく、箱庭上で配置・導線・衝突判定を統一するための論理単位である。

1セルには次の状態を持てる。

- `floor`: 床が存在する
- `buildable`: 設備設置可能
- `walkable`: 人が歩行可能
- `occupied`: 施設本体が占有
- `reserved`: 施設利用のため空ける必要がある
- `portal`: 出入口・接続点
- `blocked`: 壁・床外など通行不可

これらは単一フラグではなく、用途別レイヤーとして管理する。

## 1.3 床境界

床は論理矩形で定義する。

```js
{ minX, maxX, minY, maxY }
```

床の画面上の菱形は論理境界から投影して生成する。CSS側に別の菱形サイズを手書きしてはならない。

つまり、今後は「床の見た目」と「配置可能範囲」がズレない構造を正とする。

## 1.4 マップレイヤー

最低限、次の4レイヤーを分離する。

### A. Terrain Layer

床そのもの。

- 床内
- 床外
- 将来拡張可能領域

### B. Occupancy Layer

施設本体が物理的に占有するセル。

- 島本体
- 受付
- 壁
- 自販機等

### C. Reservation Layer

施設を利用するために空ける必要があるセル。

例:

- 椅子列
- 台を操作する側
- 受付前
- 出入口直前

予約セルは「施設本体ではないが、別施設を置いてはいけない」領域である。

### D. Navigation Layer

歩行可能性を表す。

原則:

```text
floor && !occupied && !blocked = walkable候補
```

ただし reservation の種類によっては歩行可能であり得る。

## 1.5 配置の原則

施設配置は必ず次の順序で判定する。

1. グリッド整数か
2. 床内か
3. 本体 footprint が衝突しないか
4. reservation が他施設本体と衝突しないか
5. 必須アクセスセルが確保されるか
6. 入口から必要アクセスセルまで到達可能か
7. 最低通路幅を破壊しないか

1つでも失敗すれば配置不可。

# 2. 施設基盤

## 2.1 全施設は同一スキーマで扱う

施設は種類ごとにCSSクラスだけを持つのではなく、必ず論理定義を持つ。

最低スキーマ:

```js
{
  id,
  type,
  x,
  y,
  orientation,
  footprint,
  hardCells,
  reservationCells,
  accessPorts,
  renderProfile
}
```

## 2.2 orientation

施設の向きは4方向を標準とする。

- `E`: +x方向
- `S`: +y方向
- `W`: -x方向
- `N`: -y方向

疑似2D画面上では各方向が斜め軸へ投影される。

方向変更時は footprint、reservation、accessPorts を同じ回転規則で変換する。

見た目だけ回転して論理 footprint を据え置くことは禁止。

## 2.3 footprint

`footprint` は施設本体の物理占有範囲。

矩形設備は幅 `w`、奥行 `d` を基準とし、必要に応じてセル集合へ展開する。

施設本体セルは原則 `walkable = false`。

## 2.4 access port

`accessPort` は人がその施設を利用するために立つ・接近する論理接続点。

```js
{
  name,
  offsetX,
  offsetY,
  role,
  required: true
}
```

例:

- 島: machine-seat / aisle-side
- 受付: customer-front
- 入口: enter / exit

将来の客AIは施設そのものの座標ではなく accessPort を目的地にする。

## 2.5 reservation

施設周辺の「置いてはいけない空間」を施設自身が宣言する。

例:

- 椅子が必要な1列
- 通路として最低確保したい帯
- 扉の開閉領域

この仕組みにより「見た目では置けるが人が使えない施設」を防ぐ。

## 2.6 9台島の正式規格 v1

確定済み9台島ビジュアルは内部形状を変更しない。

論理上の施設規格は次とする。

```text
本体幅       : 9セル
本体奥行     : 1セル
利用面       : S側を標準
椅子帯       : S側に1セル
歩行帯       : 椅子帯のさらにS側へ最低2セル
島間クリアランス: 本体同士で最低3セル
```

標準配置を上から論理的に見ると:

```text
MMMMMMMMM  <- 島本体 9x1
CCCCCCCCC  <- 椅子/利用帯 9x1
.........  <- 歩行帯 1
.........  <- 歩行帯 2
```

`M` は hard occupied。
`C` は reservation + interaction。
`.` は walkable を維持する必須通路。

重要:

- 9台島を横に4本直列に並べるのではない。
- 9セルの長辺を同じ方向へ揃え、複数島は短辺方向へ平行配置する。
- 「島間3マス」は長辺の終端間隔ではなく、平行する島本体同士の短辺方向クリアランスを指す。

この定義により、現行13までにあった「x方向へ島をずらして4列に見せる」考え方を廃止する。

## 2.7 9台島の描画ピッチ

論理9セルと実際の9台ビジュアルは一対一対応させる。

確定済み9台コンポーネントの1台ピッチは 344px。

画面上の1セル長辺方向のベクトル長は:

```text
sqrt(13^2 + 6.5^2) ≒ 14.534px
```

よって、1台ピッチを1セルへ厳密に合わせる基準スケールは:

```text
14.534 / 344 ≒ 0.04225
```

従来の `0.043` は近似値だったため、基盤規格では `0.04225` を基準値とし、見た目補正が必要な場合も論理ピッチを壊さない範囲に限定する。

## 2.8 入口

入口は単なる表示パーツではなく `portal` とする。

入口には最低1つ以上の内部側 portal cell を持たせる。

導線検証はこのセルを起点に行う。

入口直後が施設本体で塞がれている配置は不可。

## 2.9 壁

壁はセルまたはセル辺を占有する境界設備とする。

v1ではセル占有方式から始めてもよいが、最終的には `edge blocker` として扱える構造へ拡張可能にする。

# 3. 導線基盤

## 3.1 導線は装飾ではなく配置成立条件

導線は客AI実装前から存在する。

施設を置けるかどうかは「入口から使えるか」で決まる。

したがって、経路探索は4以降の客AI機能ではなく、1〜3の基盤に含める。

## 3.2 walkable graph

各 walkable cell をノードとし、基本接続は4近傍とする。

```text
(x+1,y)
(x-1,y)
(x,y+1)
(x,y-1)
```

斜め8近傍は使わない。

理由:

- 細い隙間を斜め抜けする不自然な経路を防ぐ。
- 通路幅の意味を明確にする。
- グリッド配置との対応を維持する。

## 3.3 到達可能性

最低限、次を保証する。

- 入口内部 portal から全必須施設 accessPort へ到達可能。
- 入口が完全孤立しない。
- 通路が施設配置によって分断されない。

施設の `requiredAccess = true` な port に到達できなければ配置全体を invalid とする。

## 3.4 経路探索アルゴリズム

v1は BFS を標準とする。

理由:

- 全辺コストを1とするため最短セル数が得られる。
- 小規模箱庭では実装が単純で検証しやすい。
- A*への移行が容易。

将来マップ拡大時に A* へ差し替え可能なAPIにする。

推奨API:

```js
findPath(start, goal, navigationMap)
canReach(start, goal, navigationMap)
floodReachable(start, navigationMap)
```

## 3.5 最低通路幅

本作の初期基準:

- 一般通路: 2セル以上を標準
- 島間: 島本体間3セルを最低クリアランス
  - うち1セルは椅子/利用帯に使われ得る
  - 残り最低2セルを歩行帯として確保
- 入口前: 2セル以上の奥行を予約
- 受付前: 最低1セル、推奨2セル

「通れる1セル」と「店舗として自然な最低幅」を分けて扱う。

BFS上は1セルでも通行可能だが、配置バリデーションでは用途別の最低幅を別途要求する。

## 3.6 通路幅判定

単純な「島の座標差」だけでは判定しない。

通路規格は reservation/clearance セルを生成し、実セル同士の衝突で判定する。

これにより向き変更や異形施設にも対応する。

## 3.7 描画順

描画順は手書き z-index ではなく論理深度を基本とする。

基準:

```text
depth = maxX + maxY
```

同深度では施設種別の小さな bias のみ許可。

`rise` は深度計算に使わない。

これにより施設を移動しても前後関係が自動追従する。

# 5. 実装禁止事項

1〜3が完成するまで以下は禁止する。

- 客数を増やして賑わいを演出する
- ランキング追加
- 新イベント追加
- 新しい経営パラメータ追加
- 吹き出し・ハート・コイン等で完成感を演出する
- CSSの手置き座標で配置問題を隠す
- 9台島内部形状の独自改変
- 「見た目がそれっぽい」ことを理由に論理規格を崩す

# 6. 実装順序

Phase A: Map Contract

1. floor bounds を唯一の床定義へ
2. cell layers を作る
3. floor polygon/grid を論理マップから描画

Phase B: Facility Contract

1. orientation utility
2. footprint transform
3. reservation transform
4. access ports
5. 9台島規格を正式データ化
6. 入口・受付・壁を同じfacility schemaへ

Phase C: Navigation Contract

1. navigation map
2. BFS
3. portal → accessPort 到達性
4. corridor width validation
5. placement validator統合

この3 Phaseが終わって初めて、客AI以降へ進む。
